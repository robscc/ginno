钉在屏幕上的聊天框

定位

它解决什么问题

Ginno 主窗口是完整的 agent 工作台，但「切过去」这个动作本身就是打断。悬浮速聊窗把最小可用的一问一答钉在所有窗口之上——它是主工作台的卫星，不是替代品。

边看边问

读网页 / PDF / 日志时，选中片段直接丢进悬浮窗提问，视线不离开当前内容。

长任务监工

主窗口里 agent 在跑构建、测试、批量修改；胶囊态绿点报状态，展开看进度、随时追加指令。

会议与演示

投屏时不切走窗口，让 agent 悄悄查个资料、算个数（注意：悬浮窗会被截屏录到，见「坑」）。

便签式 AI

翻译、改写、记一条想法。常驻置顶 = 零成本唤出，用完 Esc 收回去。

形态方案

三个候选，推荐 B

你说「界面就简单地要一个聊天框」——三个方案里 B 是字面意义上的聊天框；A 更像搜索启动器；C 存在感过强。B 还能通过胶囊态吸收 C 的常驻监工诉求、通过快捷键唤起吸收 A 的召唤体验。

推荐

  1. 标题栏 / 拖拽区 — 整条可拖动窗口；双击任意空白处收起为胶囊。
  2. 会话标识 — 显示当前模式：「快速会话」或「跟随 · <主窗口会话名>」，点击切换（见会话模型）。
  3. 状态点 — 绿=agent 运行中，灰=空闲，橙=待你确认。胶囊态同样显示这颗点，这就是「监工」的最小界面。
  4. 消息流 — 流式 Markdown；代码块限高 3 行，点开展开；历史仅保留本会话，滚动加载。
  5. 工具调用行 — 折叠为一行「⚙ 命令 + 结果」，点击展开完整输出。悬浮窗寸土寸金，agent 的过程细节默认收起来。
  6. 内联确认 — 权限请求（运行命令/写文件）以按钮形式出现在消息流里，就地决策，不弹系统对话框、不跳主窗口。
  7. 输入框 — 自动增高 1–5 行；↵ 发送，⇧↵ 换行；支持粘贴图片/文本片段。
  8. 快捷键提示 — ⌘↵ 把当前对话移交主窗口继续。

可行性

技术要点（Tauri v2）

结论：现有架构完全支撑，无需动 sidecar / PyInstaller 链路。悬浮窗是第二个 WebviewWindow（label: pin），加载同一前端的新路由 /pin，连同一条 ws://127.0.0.1:8787 流。

窗口壳（Rust 侧）

  • always_on_top(true) + decorations(false) + transparent(true) + shadow(true)，resizable(true)
  • set_visible_on_all_workspaces(true)（Tauri v2 内置 macOS API）实现跨 Space
  • 层级微调走 NSWindowLevel（.floating）；全屏 Space 避让策略需 NSWindowCollectionBehavior 定制
  • 胶囊态点击穿透：set_ignore_cursor_events(true)
  • 全局快捷键：官方 global-shortcut 插件；注册失败（冲突）时降级为菜单栏入口并提示

前端与会话（复用为主）

  • 新路由 /pin：复用现有聊天组件，新增 compact 变体（限高代码块、折叠工具行、内联确认按钮）
  • 会话：runtime 新增 session.type = "quick"，checkpoint 走现有文件式 checkpointer，无 schema 变更
  • 「接管」= 主窗口 deep link 到该 session id，消息历史天然连续
  • capabilities/ 需为 pin 窗口补多窗口与 shortcut 权限
  • 主窗口与悬浮窗同时订阅同一会话时，WS 多路复用/去重需要设计（风险点）
规模预估：窗口壳与状态机 ~1 天，compact 聊天 UI ~1.5 天，快速会话与接管 ~1 天，设置/快捷键/打磨 ~1 天。属于一个独立 worktree 可完成的中型 feature。
需要你拍板

5 个开放问题

这些答案会直接改变实现方案，先定了再出实施计划。

Q1

悬浮窗里的 agent 要多少能力？

完整 agent（能跑命令、改文件，确认内联在悬浮窗里）？还是轻量问答（只聊天 + 只读查询，需要动手时提示移交主窗口）？这决定 confirm 交互和权限体系的复杂度。

建议完整能力 + 内联确认——它是「卫星」不是「玩具」，能力阉割会让长任务监工场景落空。
Q2

默认会话模式是独立快速会话，还是跟随主窗口？

独立 = 干净、随问随答；跟随 = 打开即见主窗口 agent 在干什么。两者都做（可切换）成本可控，但要定一个默认值。

建议默认独立快速会话，「跟随」做成会话标识处的下拉切换。
Q3

其他 app 处于 macOS 全屏 Space 时，悬浮窗覆盖还是避让？

macOS 特有决策：全屏 Space 里强行置顶技术上可行但极易挡事（比如全屏看视频）；自动避让则「永远置顶」名不副实。

建议做成设置项，默认「避让全屏 Space、胶囊仍在」，想看时快捷键临时覆盖。
Q4

常驻形态：菜单栏图标 + Dock 隐藏，还是维持现状？

若悬浮窗要「关主窗口也活着」，app 需要支持菜单栏常驻（甚至 LSUIElement 隐藏 Dock 图标），这是激活策略层面的改动。

建议v1 先做菜单栏图标 + Dock 保留；LSUIElement 纯后台模式留到 v2。
Q5

胶囊态要不要点击穿透的「状态灯」模式？

穿透后胶囊完全不拦截鼠标、纯当 agent 状态指示灯；代价是想展开必须先按快捷键。实现很便宜（一个开关）。

建议做，默认关。长任务挂机场景下很好用。
盲区提示

macOS 特有的坑（提前知道好过事后踩）

  • 截屏 / 屏幕共享会录到悬浮窗——置顶窗口出现在所有截图和投屏里。演示场景要么提前收起，要么后续考虑「截屏时自动隐藏」（macOS 有对应 API，v2 再说）。
  • 快捷键冲突——⌥Space（Raycast）、⌘Space（Spotlight）、⌃Space（输入法）都是雷区；默认值要避开且注册失败时优雅降级。
  • 全屏 Space 与 Stage Manager——always-on-top 窗口在这两种模式下的行为是 macOS 版本相关的老大难，Q3 的策略必须在真机上逐版本验证。
  • 多显示器 + 刘海——位置记忆要按显示器分别存；刘海下方是死区，吸附逻辑要避开。
  • 透明窗口 + 圆角——Tauri 透明窗在 macOS 上需要正确处理阴影与圆角裁剪，否则四角出现黑底。
