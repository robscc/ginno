为什么是状态卡而不是 live 多列对话？
方案 B（herdr / Claude Squad 式工位墙）每列都挂活 WS + 活渲染，4 路并行在笔记本上已经捉襟见肘。 这里只订阅一个 team.changed 聚合事件 + 每卡最近 3 行摘要，把「谁卡住了」的可见性拉满而不付多 WS 的代价。 要看全文点卡片进成员工作台（那才是完整 ChatStream）。

状态判据（零新事件，纯聚合现有信号）： working = session 在 _RUNNING_TURNS 且无 pending interrupt · blocked = 有未答的 permission / ask_user 卡 · waiting = turn 已结束但还有运行中子代 · done = turn 结束且本客户端未 seen · idle = 无 turn 无 pending 已 seen · unknown = 重启后不可判定 · error = 重试耗尽。

Ginno 相对 herdr 的结构性优势：herdr 站在 agent 外面读终端屏幕猜状态， 所以 blocked 检测必须「deliberately strict」，匹配不上就 fallback 到 idle 并承认会误判 （"unusual new prompts may initially show as idle instead of blocked"）——为此它要维护 22 个 agent 适配清单、 manifest 版本协商、远程规则热更新、本地 override 优先级、以及 herdr agent explain 调试命令。 Ginno 站在 agent 里面：permission / ask_user / turn 边界都是 runtime 自己发的结构化事件， blocked 是权威零误判的，新增 agent 类型自动获得完整状态语义，不需要任何适配工作，也不需要 explain。
反过来该学 herdr 的：它对状态语义的严谨度（done/seen/unknown 三分、上卷优先级、投递原子性、超时≠未发送） 不是终端形态特有的，是多 agent 可观测性的通用真理 —— 本方案已逐条吸收。
