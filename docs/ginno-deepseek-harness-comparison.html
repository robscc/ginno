00摘要

四路独立调研（Ginno 本地全仓代码与文档；dsh 架构/功能/工程化三路代码级深读，浅克隆 @2026-08-30）后的核心判断：

  • 这不是同级竞技，而是两个量级的对话。DeepSeek Harness（下称 dsh）是 DeepSeek 官方开源的 agent harness 平台：开仓 17 天 20.4 万 stars / 2.36 万 forks，3248 个 PR，51 个包、近 9000 文件，10 天 5 个 release。Ginno 是六周龄的个人本地 agent：141 commits、334 个源文件。对比的价值不在胜负，而在「能力图谱对照」与「工程实践借鉴」。
  • 能力图谱惊人同构。skill（都用 SKILL.md + frontmatter）、todo、goal、workflow、hooks、subagent、上下文压缩、MCP、权限审批——两边独立收敛到了同一张 agent 产品概念表。这本身验证了 Ginno 的产品判断与业界形态一致。
  • 「workflow」同名不同种，这是对比的最大看点。Ginno 的 workflow 是持久化业务流程引擎（DSL → LangGraph 编译、checkpoint 恢复、重试/超时、并行 gather、human 审批节点、dry-run、doctor、L0-L4 质量漏斗）；dsh 的 workflow 是一次性 JS 编排脚本（agent()/pipeline()/parallel()/phase()，无文件系统/网络、无持久化、无人机闸门）。在「可恢复、可审批、可度量」这条轴上，Ginno 反而显著领先。
  • Ginno 的独有资产在 dsh 里找不到对应物：会话→workflow 自动合成（summarize-from-session）、L0-L4 合成质量漏斗与案例台账、todo 勾选即触发、[sN] 引用契约与 cite_rate 遥测、workflow 版本 diff 审批（version_propose）。
  • dsh 的绝对长板：Cordis 全插件化（连 agent 循环本身都是可换插件）、三平台原生沙箱（含 ~300 行 C11 的 landlock 自限权 launcher）、五端形态（CLI/Web/Python SDK/TS SDK/ACP）、工程化基础设施（7 层测试金字塔、会话快照回放、per-file 100% 覆盖率门禁、门禁 DAG、双语 i18n 机器强制）、DeepSeek V4 深度集成（1M 上下文 / 256K 输出 / Files API）。
  • 最值得 Ginno 借鉴的不是架构的平台性，而是工程实践：会话快照回放测试（record/replay/refresh 三态，正面解决 LLM 应用测试贵且不确定——可直接用于 Ginno 的合成评测）、自动生成的工具目录 + 完整性守卫、门禁 DAG（本地复现 CI，Ginno 目前无 CI）、defensive-patterns/postmortem 文档层。全插件化 / profile 体系 / 品牌秩序则是平台玩法武器，个人产品不必跟。

02产品定位：两个量级，两种打法

Ginno
为一个人深耕的本地 agent

Ginno 的产品重心是「把我的工作方式固化下来」：对话产出的好流程能蒸馏成 workflow（summarize-from-session），todo 勾选能直接触发自动化，知识以本地 wiki + 语义检索沉淀，引用有契约、用量有台账。本地优先（~/.ginno/ 纯文件，无数据库、无服务端），隐私边界清晰。

workflow 三分法（TODO=要做什么 / Workflow=怎么做 / Goal=达成什么）与「运行回到对话」的体验设计，都服务于单人深度使用。

来源：README、goal-design.md、workflow-dsl-design.md

DeepSeek Harness
模型厂商的 agent 底座与生态宣言
「DeepSeek Harness (dsh) is an open-source agent harness developed by DeepSeek AI. It is built on an everything-is-a-plugin architecture and powered by Cordis.」README.md

dsh 是 DeepSeek 对「agent 产品应该长什么样」的官方回答：无特权核心——模型适配器、工具注册表、会话日志、agent 循环本身全是插件，配置可换；一切经 profile 组合、补丁层叠加。配套商标指南、Discord、插件话题标签（dsh-plugin）——这是以品牌秩序运营的生态平台，不是个人工具。

来源：README.md、BRAND_GUIDELINES.md、docs/architecture.md

判断　两者服务对象不同：Ginno 做「我的 agent」，dsh 做「所有人的 agent 地基」。这决定了后续所有差异的解读方式——dsh 的插件体系、多端形态、品牌机制是平台武器；Ginno 的会话蒸馏、质量漏斗、个人触发是深耕资产。跨量级对比的正确姿势是：从平台身上学工程与抽象，而不是复制平台形态。

03架构对比：六个剖面

3.1 扩展模型：全插件化 vs 注册表模式

dsh · Cordis
时空可组合性
  • 五概念：plugin=Service；Context 是服务仓库（ctx.tools/ctx.llm/ctx.sessions）；依赖经 inject 声明——所需服务就位才激活，以服务依赖取代启动排序；类型化事件（5 种派发：emit/waterfall/parallel/serial/bail）；注册皆为可逆 effect，卸载自动回卷。
  • 无特权核心：agent 循环（ReactLoopAgent）只是默认驱动插件，可整体替换。
  • 空间组合：Profile（命名组合）× Bundle（补丁层分发单元）；--dump-config 打印的每一行都可被 patch 替换；热重载。
  • Capability Seam：fs/subprocess 抽象成 Provider/Consumer 三角色——换到 E2B 远程沙箱，Bash/PTY/LSP 跟着整体迁移（packages/e2b/ 三个包实证）。

来源：docs/cordis-primer.md、architecture.md、capability-seams.md（Cordis 论文：arXiv 2608.25512）

Ginno · 注册表
产品级扩展点
  • 节点注册表：@register_node 装饰器插件化（workflows/nodes/），内置 8 类节点。
  • Agent 注册表：agents/registry.py 四内置（dev/research/writer/workflow-dev），tools_allow 过滤，可 fork 自建。
  • Skill loader：SKILL.md frontmatter 声明触发方式；todo provider：外部平台经 skill 声明 todo_provider 免写 adapter。
  • 核心是特权的：LangGraph 图结构、权限节点、主循环不可替换——扩展发生在预留的挂点上，而非任意树节点。

来源：packages/runtime/src/ginno_runtime/{workflows/nodes,agents,skills,todos}

判断　这是「平台级可组合性」与「产品级扩展点」的哲学差。dsh 的组合性有论文背书和真实收益（换沙箱搬走整个工具面）；代价是概念门槛与调试复杂度。Ginno 的注册表对个人产品是恰当复杂度——需要警惕的不是「不够插件化」，而是扩展点别变成一次性接口。

3.2 状态模型：事件溯源 vs 文件 checkpoint

dsh
会话 = append-only 事件日志

事件溯源为单一事实源：deriveMessages() 投影出模型历史；不变式「Model-visible means logged」。fork / resume / transcript / 遥测全部从日志派生。双后端：JSONL + SQLite（SESSION_FORMAT_VERSION=0）。session 事件（持久事实）与 agent/* 事件（实时协调）双轨。

Ginno
checkpoint + 文件台账

FileCheckpointer（LangGraph checkpoint 落文件）支撑暂停/恢复/失败重试；用量走 ~/.ginno/usage/*.jsonl 归一化台账；合成案例走 ~/.ginno/synthesis/ 台账。各域文件化、可读、可 grep，但没有统一的事件层。

判断　事件溯源让 dsh 免费获得会话搜索（5 个只读检索工具、SQLite FTS5）、fork、快照回放测试。Ginno 若未来做「会话内搜索」「运行分叉」，会自然走到这条路上——但现在文件台账的简单性仍是资产。

3.3 主循环

dsh 的一个 turn = 0..n 个 step（一次模型请求 + 其工具调用）； Ginno 的一轮 = LangGraph 超步。

turn/start → claim声明所有权
agent/pre-stepwaterfall：可 reject/改写
assemble prompt → agent/request组装并请求
llm/stream适配器可拦截
tool/callpre→guards→approval→execute→post
step/end → turn-stopping判停
agent模型决策
permission人机授权闸门
tools按 agent 过滤执行
agent回环；可 interrupt
判断　dsh 把拦截点做成事件瀑布（任何插件可在 pre-step / tools/pre 挂策略，无需 import 循环）；Ginno 把拦截点做成图节点（权限是一等节点，interrupt/resume 是引擎能力）。前者开放，后者显式。

3.4 LLM 接入层

  • dsh：ctx.llm 适配器注册表 + 可 waterfall 拦截的流式调用。双适配器：llm-deepseek（官方协议：V4 Flash/Pro/Vision、thinking/reasoningEffort、默认 256K maxTokens / 1M context、Files API 上传卸载）与 llm-pi-ai（通用，接 openai/anthropic 等）。key/endpoint 按请求解析，改动下个请求即生效。
  • Ginno：langchain-openai / langchain-anthropic / ollama，provider 中立；用量归一化（含 cache_read/creation token 形状）。

3.6 Host/Client 边界

dsh 的 TS 按 host/client 双面编译；Typert 网关不是模型网关，而是 Host↔Client 的 RPC 网关：@Remote 装饰器 + 构建期从 ts.Program 提取双端契约，生成 POST /api/<ns>/<method>。客户端调 ctx.remote.<ns> 的具体生成函数——类型安全贯穿两端。Ginno 的对应物是 FastAPI 路由 + WebSocket 事件流（workflow.emit 等），手写契约。

亮点　dsh 有大量「文档/契约由 TS Program 自动生成并校验」的实践：工具目录、模块图、事件生产消费矩阵、capability 图（scripts/gen-doc-graphs.ts）——机器保证文档不漂移。这是本报告反复出现的主题：把一致性从自觉变成机器强制。

05编排深潜：同名不同种的 workflow

这是整份对比里最值得写的一节。两个项目都有叫「workflow」的一等能力，但它们解决的根本不是同一个问题。

5.1 两种形态

Ginno · 持久化业务流程引擎
「把这次好用的对话变成下次可重放的脚本」
  • 载体：JSON DSL（dsl.py 单一事实源，dsl_version=1），编译为 LangGraph StateGraph 流式执行。
  • 节点：step(agent) / llm / branch / loop / human / pass / python（确定性白名单）/ extract（编译器注入）。
  • 可靠性：每节点 retry（1-10 次，fixed/exponential backoff）+ timeout_s + on_error=stop/continue；显式 recursion_limit 防死循环。
  • 并行：loop.parallel + gather（max_concurrency 1-8，index 序合成，全局门控）。
  • 持久化：FileCheckpointer，支持 resume（interrupt 恢复）/ continue（失败重试）/ 手动暂停通道。
  • 人机闸门：human 是一等 interrupt 节点；supervisor intervene 可 patch DSL；version_propose 弹 diff 审批后才创建不可变新版本。
  • 版本化：versions / rollback / diff_versions。
dsh · 一次性编排脚本
「把一群 subagent 的分工写成代码」
  • 载体：JS 脚本，API 为 agent() / pipeline() / parallel() / phase()；Workflow 工具确定性执行（无文件系统、无网络）。
  • 单元：agent() 起一个 subagent 跑 prompt 返回结构化结果；pipeline 串联、parallel 扇出、phase 分段。
  • 生命周期：随调随跑、跑完即弃。无 checkpoint、无跨重启恢复、无版本、无人机闸门（审批发生在工具层而非编排层）。
  • 亲属：ralph（fresh-agent 轮询循环）、run_code（TS 代码并发调工具）——都是「用代码驾驭 agent」的临时手段。
  • 质量保障：靠 schema 约束 agent() 返回 + 快照回放测试，无生成质量漏斗。

5.3 为什么会这样分叉

dsh 的世界观里，强单 agent + subagent 扇出是主答案：复杂任务拆给一群一次性 subagent，编排代码是草稿纸，用完即扔；持久性交给会话日志（事件溯源），不交给流程。所以它不需要流程级的 checkpoint 和人审节点——审批在工具层（每次副作用调用都过 guards/approval）。

Ginno 的世界观里，流程是资产：用户把一次满意的协作蒸馏成配方，此后确定性重放、版本演进、失败可恢复。流程活得比会话久，所以必须有持久化、闸门和度量。

判断　在「可恢复、可审批、可版本化、可度量」这条轴上，Ginno 的实现深度领先 dsh——这不是体量差距能解释的，是路线选择。dsh 的编排为「一次性多智能体任务」优化，Ginno 的编排为「重复发生的业务流程」优化。前者是业界主流叙事，后者是更窄但更深的生态位。风险提醒：这条轴的价值取决于「个人用户是否真的有重复流程要固化」——Ginno 的 L0-L4 漏斗本身就是回答这个问题的度量装置，值得持续盯住 L3/L0 与 L4/L3 两个比值。

5.4 触发器与无人值守：两边都还没过关

上一份对比报告（Ginno × OpenHuman）指出「触发器 + 无人值守安全闸门」是 Ginno 的最大缺口。有趣的是，dsh 也没有给 workflow 配触发器：它的自动化答案是 schedule（会话内提醒，≥300s 粒度，无 cron、不跑 workflow）、webhook（GitHub 签名 webhook 自动建审查会话）与 goal 自动续轮。换句话说，「无人值守跑完整业务流程」在两个项目里都还没有产品级答案——这个空档既是行业共同的未竟之地，也再次印证触发器必须与安全闸门成对引入（自动触发的东西必须有审批边界）。

09借鉴清单：dsh → Ginno 行动

按成本分三层。筛选标准：可迁移性（个人产品用得上）× 回报率（解决的痛点真实存在）。

9.1 第一层：低成本高回报（可立即排期）

01会话快照回放测试（record / replay / refresh）最高优先

dsh 用它正面解决了「LLM 应用测试贵且不确定」：录制真实会话（输入 + 模型输出），回放时确定性 diff 组装请求/转录/持久化，keyless、可并行、PR 强制。Ginno 的两处直接受益点：① 合成链路（synth-5）的回归评测——目前靠案例台账手工回填，快照化后 L0-L4 漏斗的「合法率/采用率」可以自动跑；② e2e 从 fake model 升级为「录一次真模型，永久回放」。

落地 在 tests/ 加第三态目录：录制脚本（一次性真跑，存 session.jsonl + 期望）→ 回放 runner（注入录制响应，断言事件序列）→ refresh 命令重录。先覆盖 1 个合成场景 + 1 个 workflow 运行场景。
02门禁 DAG + 最小 CI高优先

Ginno 目前无任何 CI，发布前校验靠手动跑全量。dsh 的 run-gates.ts 思路——把所有校验（测试、tsc、cargo、sidecar 构建、文档链接）编排成带依赖的 DAG，一条命令本地复现——把「记得跑」变成「一键跑」。哪怕不上 GitHub Actions（私有仓库），一个 make check 也有巨大价值。

落地 Makefile 增 check target 串联现有校验 + 新增文档链接检查；后续若仓库上私有 CI，直接复用同一 DAG。
03自动生成的工具/节点目录 + 完整性守卫

dsh 的工具目录由脚本从注册表生成，CI 守卫「新工具不可能漏文档」。Ginno 的 8 类 workflow 节点、4 个内置 agent、工具族都在代码里，文档靠手写。生成 + 守卫的成本极低（一个脚本 + 一个测试），收益是文档永不漂移。

落地 脚本遍历 @register_node / agents registry / builtin tools，生成 docs/tool-node-catalog.md；测试断言生成内容与文件一致。
04defensive-patterns + postmortem 文档层

dsh 把 bug 复盘沉淀为两层文档：postmortem（事故叙事，如 0001 ACP default export 丢 inject → 催生「冒烟测试优先」政策）与 defensive-patterns（bug-class 规则集）。Ginno 已有 implementation-notes 传统与真实事故（2026-08 stock-workflow 的 loop.over.no_source），只差形式化：复盘直接改测试政策，规则集成为 doctor 规则与 code review 检查表的来源。

落地 docs/ 开 postmortem/ 目录（编号制），每篇必须含「政策变更」段；doctor 新规则注明对应复盘编号。

9.2 第二层：与演进绑定

05per-file 覆盖率门禁（渐进式）

dsh 的哲学是「未覆盖的行≈死代码，删除或补测」，豁免必须写理由。Ginno 不必一步到位，但可以先对新增模块（如合成评测）上文件级门禁，把覆盖率从「总量好看」变成「无死角」。

落地 pytest --cov 配 fail_under 白名单制：新模块默认 100%，存量模块冻结线逐步抬升。
06hooks 协议向 Claude Code 格式看齐

dsh 直接兼容 Claude Code / Codex 的 hooks.json——生态里已有的钩子脚本零成本可用。Ginno 的 hooks dispatcher 是自有格式；若向主流格式靠拢，等于免费接入一个现成生态。成本低（格式映射），但要先确认 Ginno 的事件点与对方语义能对齐。

落地 调研 Claude Code hooks 的事件点集合，对照 Ginno dispatcher 现有事件，出兼容性映射文档再动手。
07bash 沙箱化（Seatbelt profile）

见 §6：现有路径治理 + 进程级边界互补。dsh 的 macOS seatbelt 实现（含拒绝消息格式）是现成参考，MIT 许可。若 Ginno 启动无人值守议程，此项升级为前置条件。

落地 参考 dsh packages/sandbox 的 seatbelt 实现，为 bash 工具包一层 sandbox-exec profile：workspace-write 模式 + 家目录只读白名单。

9.3 第三层：长线选项

08事件溯源的局部引入

dsh 的会话搜索（5 个检索工具）与快照回放都建立在事件溯源上。Ginno 若未来做「搜历史会话」「运行分叉」，会自然走到这条路。现阶段可先不动架构，但在设计新功能时问一句：这个状态将来要不要被检索/回放？

落地 不必现在动手；在 docs/architecture.md 记为已评估选项。
09runtime SDK 化

dsh 证明 harness runtime 可以封装成 SDK（Python wheel 自带可执行）对外供给自动化场景。Ginno 的 FastAPI sidecar 天然适合做这一步——若出现「让别的程序调 Ginno 的 workflow」的需求，先出 SDK 而不是 UI。

落地 等需求信号；先保持 API 面稳定即是最小准备。

9.4 不建议跟的

  • 全插件化 / profile-bundle 体系：平台玩法的武器。个人产品引入「一切皆插件」只会把调试复杂度指数化——Ginno 的注册表扩展点是恰当复杂度。
  • 多端齐发：dsh 的五端服务生态占位；Ginno 的桌面单端是产品选择，别被「应该有 CLI/SDK/ACP」的完整性焦虑带偏。
  • 会话日志上传（dsh_session_log）：与 Ginno 本地优先哲学冲突，碰都不要碰。
  • 品牌秩序类产物（商标指南、插件话题标签运营）：生态位不同。
  • 「无外部 PR」的开发模式：那是深怕生态失控的平台策略；私有个人项目无所谓，但若将来开源，别学这条。

10结论

  • 一句话定位：dsh 是 DeepSeek 对「agent 操作系统」的官方答卷，Ginno 是为一个人深耕的「agent 手艺人作品」。前者赢在面、工程与生态位；后者赢在深——尤其是 workflow 的可靠性与质量度量。
  • 判断一：能力图谱已经业界收敛。两边独立长出同一张概念表（skill/todo/goal/workflow/hooks/subagent/compaction/MCP/审批，连 SKILL.md 格式都撞车）。Ginno 的产品方向不需要自我怀疑。
  • 判断二：workflow 是 Ginno 的护城河，继续挖深。dsh 用「强单 agent + 一次性编排」绕过了持久化流程的所有难题；Ginno 正面解决了它们（checkpoint/闸门/版本/漏斗）。只要「个人用户有重复流程要固化」这个前提成立，这条轴上的领先就是真实资产。用 L0-L4 比值持续验证前提本身。
  • 判断三：学工程，不学形态。dsh 最值得搬的是四件工程实践——快照回放测试、门禁 DAG、生成式目录 + 守卫、复盘文档层——全部低成本可迁移。全插件化、多端、生态运营属于平台的武器库，个人产品背上只会变慢。
  • 未竟之地：无人值守跑完整业务流程（触发器 + 安全闸门成对），两个项目都还没有答案。这既是共同的空档，也是 Ginno 若要做「自动驾驶」前必须先补的课——与上一份对比报告（Ginno × OpenHuman）的结论互相印证。
