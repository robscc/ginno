# 用量点格图 — 产品设计

> 状态：设计已定，待实现。原型 `docs/design/prototypes/usage-grid-prototype.html`
> （内置你机器上 41 天真实 `~/.ginno/usage` 记录，非假数据）。
> 上游文档：`usage-stats-design.md`（schema / API / 保留策略）。本文只覆盖 Overview 的时间视图改造。

## 1. 要解决的问题

现有 Overview 的时间视图是两张图：**每日堆叠柱图** + **24 小时分布柱图**。
两张都在回答「什么时候花的」，但都答得不准：

- 每日柱图能看总量趋势，看不出一天之内是「上午一阵」还是「全天磨」。
- 24 小时柱图把 41 天压成一条平均曲线，正好把上下班节奏压平了——你 8 月和 10 月
  的作息完全不同，图上只剩一个均值。

点格图把这两个维度合到一张图上：**横轴是日期，纵轴是一天里的 2 小时桶**，
一眼同时读出「哪天」和「几点」。

## 2. 已定决策

| 项 | 决策 |
|---|---|
| 朝向 | 每天一列，12 行 = 24 小时，每行一个 2 小时桶 |
| 颜色编码 | 总 token，5 档（不再显示 p50 等分位标记） |
| 分档方式 | 窗口内非零格取 P20/P40/P60/P80 五等分，自动重算 |
| 与旧图关系 | **替掉**每日堆叠柱图 + 24 小时分布柱图 |
| 保留 | Source / Provider / Model 三个分布面板 + KPI 行 |
| 缺口日 | 无 jsonl 文件的日子与「没干活」**样式完全相同**（同一个空格子），不留任何特殊标记 |
| 时间轴 | 连续日历（每天一列，含没有文件的日子） |
| 图例 | `Less ▫▪▪▪▪ More`，无文字说明 |

## 3. 数据现实（实测，2026-08-08 → 2026-10-08）

4,438 条请求，41 个有记录的日子，**126 个非空 2h 桶 / 492 个理论桶 = 25.6% 填充**。

**3.1 「总 token」有歧义，且差 12.7 倍**

`usage.py:13-38` 的约定：langchain 1.x 会把 cache 部分**加回** `input_tokens`。
所以 `input + output` 里，cache read 是被重复计入的。

| 口径 | 中位忙碌桶 | 峰值桶 | 其中 cache |
|---|---|---|---|
| gross = in + out | 1.84M | 42.97M | 42.6M（峰值桶的 99%） |
| net = in − cache + out | 145k | 9.19M | — |

两种口径下**最深的格子不是同一批**。gross 口径下这张图实际是「缓存上下文热力图」——
颜色深 = 会话拖得久，不是花得多。

原型保留了 `Gross / Net ex-cache` 切换用于评审这个选择。**实现前必须定死一个默认值**，
否则同一个 KPI 在两处会显示不同数字。

推荐：**默认 net**。理由——gross 让 90% 的格子被单个长会话的缓存淹没，日与日之间的
可比性差；net 反映真实新增工作量。缓存命中另由 KPI 单独承载。

**3.2 00:00–08:00 几乎全是空行**

```
每行填充数(0,2,4...22时): 4, 1, 1, 1, 9, 14, 13, 24, 27, 12, 12, 8
```

前 4 行在 41 天里总共 7 次请求。**但仍然保留 12 行**：行位置固定才能横向对比，
且「凌晨不干活」本身就是这张图要传达的信息。若将来要压缩，应该折叠成
「00–06」一行，而不是删行（删行会让纵轴在不同筛选下错位）。

**3.3 数据卫生（与本设计无关，但会污染 Model 排行）**

- `GLM-5.3-Flash` / `glm-5.3-flash` / `glm-5.3` 三个变体在 Model 排行里各占一行，
  其中前两个是同一个模型的大小写重复。
- 180 条记录 `model` 为空串，Provider 面板里显示为 `—`，占 gross 的 5.7%。

## 4. 视图规格

### 4.1 几何

- 格子正方形，尺寸 `clamp(10px, 填满卡片宽度的均分值, 22px)`，随窗口天数与卡片宽度联动。
- 格子间距 3px。
- 左侧固定小时栏（00–22，12 行），列头只在每月 1 号和首列显示日期，其余留空。
- 卡片顶部预留 34px 日期带；日期标签相对列顶 `-19px`，必须完全落在带内
  ——`.gridwrap` 是滚动容器（`overflow-x:auto` 会把 `overflow-y` 计算成 `auto`），
  超出 padding box 的内容会被裁掉。
- 小时栏**不能有** `padding-top`，否则整栏下移 19px，与格子错开一整行
  （表现为「00」标在第 2 行上）。
- 每月 1 号处画一条竖分隔线，作为周/月的视觉分段。
- 卡片宽度不足时横向滚动，左侧小时栏保持吸顶。

### 4.2 颜色

色阶**从全局 token 派生**，不另起炉灶：空格子直接用 `--card2`（描边 `--line`），
L1–L5 是 `--card2 → --chart-1` 的 20/40/60/80/100% 混合，**L5 恰为 `--chart-1` 本尊**
（globals.css 里 CVD 校验过的图表首色）。这是 GitHub 绿的做法：同一色相越涂越深，
而不是引入新色相。

| 档 | 暗色 | 亮色 | 来源 |
|---|---|---|---|
| 空 | `rgb(var(--card2))` | 同左 | `--card2` + `--line` 内描边 |
| L1 | `#21314b` | `#cbdaf0` | 20% 混合 |
| L2 | `#274672` | `#a3c2ea` | 40% 混合 |
| L3 | `#2d5c98` | `#7aa9e3` | 60% 混合 |
| L4 | `#3371bf` | `#5291dd` | 80% 混合 |
| L5 | `#3987e5` | `#2a78d6` | = `--chart-1` |

选中 / hover / 当前时段的强调色仍是 data 分组主题青绿（`#2dd4bf` / `#0891b2`），
与蓝阶色相分离——实测 L5 蓝格（`rgb(57,135,229)`）上的青绿描边
（`rgb(45,212,191)`）清晰可辨，最深档不会被读成选中态。

> 演进记录：初版色阶是手拟的青蓝 + 琥珀 L5（原型里的值），评审时发现与全局
> 配色不搭（琥珀用的是亮色 `--chart-4` 值、青蓝在 app 里不存在），改为上述
> token 派生方案。`--ug-heat-*` 变量名不变，仅值替换。

### 4.3 格子状态

| 状态 | 表现 |
|---|---|
| 无请求（当天有文件） | 空档底色 + 内描边 |
| 当天无文件 | **与上一行完全相同**——同样渲染成空格子 |
| 今日未到的时间桶 | 极淡描边，不参与分档 |
| 当前正在进行的桶 | 主题色描边 |
| hover | 主题色描边 + tooltip |
| 选中（点击） | 2px 主题色描边，再次点击或 Esc 取消 |

分档只对**有请求且已发生**的桶计算。未来桶和无文件日不进分位数样本，
否则高活跃日的档位会被空白拉偏。

## 5. 交互

- **hover**：tooltip 显示 `日期 HH:MM` + cache / in / out / 请求数。
- **点击**：钉住该桶，左面板展开 cache / 新增 input / output / gross 四项 +
  一条三段占比条；右面板展开当天 12 个桶的逐桶数值。
- **Esc**：取消钉住，恢复窗口摘要。

## 6. 页面构成

```
Overview
  KPI 行        今日 token / 今日请求 / 缓存命中率 / 区间 token    ← 4 个都保留，未加「峰值桶」
  统计窗口      近 7 / 30 / 90 天（原有，只管 KPI 与三个分布面板）
  点格图        ★新增，替掉每日柱图 + 24h 柱图
    ├ 范围      14d / 30d / 60d / All   ← 自己的窗口控件，标签刻意与上方「统计窗口」区分
    ├ 口径      Gross / Net ex-cache
    └ 详情面板  hover / 点击展开
  分布面板      Source / Provider / Model        ← 保留不动
```

**两处对本文早期版本的偏离**（实现时确定）：

1. **「峰值桶」没有进 KPI 行。** 它由点格图数据推导，放在顶行会让 KPI 变成 5 个塞进
   `grid-cols-2 xl:grid-cols-4`，而且 Overview 与 GridPanel 会各拉一次数据。改为由
   GridPanel 在自己的头部呈现。
2. **GridPanel 完全自包含，不接 Overview 的窗口。** 它自带范围控件并自行取数，
   因此与 Overview 的「统计窗口」是两个独立控件。标签已改为「范围 / Range」避免混淆。
   代价是页面上有两个窗口控件；好处是点格图能取到 `All`（90 天），而 Overview 的
   7/30/90 给不了。

轮询沿用 `OverviewPanel.tsx:82` 的 60s 定时器，接口形状不变。

## 7. 后端改动

**新增** `GET /api/usage/grid?from&to`（`api/usage.py`）：

```jsonc
{
  "ok": true,
  "days": ["2026-08-08", ...],   // 连续日历，含无文件的日子
  "grid": [                        // days.length × 12
    [ [gross, net, out, cache, requests], ... ]   // 每格 5 个整数；无文件的日子整列全 0
  ]
}
```

- 分桶按**本地时间** `hour // 2`，与原 `aggregate_hourly` 的约定一致。
- 数据来源复用 `load_day` 的 `_DAY_CACHE`，不新增预计算表。
- `from`/`to` 上限对齐 `RETENTION_DAYS = 90`。
- **不需要 `have` 字段**：前端不再区分「无文件」与「零请求」，两者渲染相同。
- 现有 `/api/usage/hourly` 在点格图上线后没有调用方，已删除（连带
  `aggregate_hourly`、`UsageHourPoint` / `UsageHourly` 类型、`getUsageHourly`、
  `StackedBars`、`SkuBreakdown` / `SkuRow`、`SeriesLegend`、`CACHE_WRITE_COLOR`、
  `niceMax`，以及 12 个随之失效的 i18n key）。

**调用方必须显式传 `from`/`to`。** 无参调用会拿到服务端默认的 30 天，
`60d` 与 `All` 会被前端切片成同样的 30 列 —— 这是实现中真实踩到的坑。
`GridPanel` 因此一次性拉满 90 天再在前端按范围切片（90×12 个格子，开销可忽略）。

**`server.py` 末尾有 SPA catch-all**（`@app.get("/{full_path:path}")` → `index.html`，状态码 200），
所以已删除的端点不会返回 404。回归测试改为断言 `/openapi.json` 的路径表。

一次请求返回全窗口，避免 41 次 `/hourly` 的 N+1。

## 9. 未决

1. **默认口径 gross 还是 net** — 见 3.1。建议 net，必须你拍板。
2. **`glm-5.3-flash` 大小写归一** — 属独立修复，可与本设计解耦。
3. **是否要按 source / model 再分一维**（例如点格图可切 chat / external）——
   当前 source 占 gross 的 98.6%，切了意义不大，建议 v1 不做。

## 10. 验收

- 62 天窗口下 744 格全部渲染，横向不溢出；14d 窗口格子放大到 22px 上限。
- 无文件日与零请求日的格子 computed style 完全一致（同一套空格子样式）。
- 小时栏每行与格子行对齐，偏差 < 1px（「00」必须标在第一行上）。
- 日期标签完全落在卡片内，不被 `overflow` 裁剪，标签之间不重叠。
- 切换 14d/30d/60d/All，格子始终保持正方形。
- hover 任一格（含无文件日、今日未来桶）不报错，tooltip 不溢出卡片。
- 亮色 / 暗色 / 跟随系统三种状态下，所有色阶均可辨认，选中态与最深档不撞色。
- 屏幕阅读器能读到每格的日期、时段与请求数。
