02

概念模型：session 服务于 workflow

与方案 A（流程是会话的投影）方向相反：Studio 是主战场，会话只剩两种从属角色。 两个入口把「已有的对话」变成流程资产，一个出口让某次运行回到聊天里盯盘。

产品方案：四屏 + Supervisor 控制台

原型与截图来自设计分支，点击任一截图可放大到原始尺寸（1440×900）。

Supervisor：工作室优先下的一等公民

治理层在检查点裁决 继续 / 重试 / 跳过 / 改 context / 暂停 / 中止。 human = 推裁决卡等人；auto = 独立 LLM 结构化裁决，只在异常时干预， 不确定或超预算就回退 human。安全阀：每步重试上限、单 run 干预上限、token 预算、confidence 回退阈值。 配置三层：DSL 默认 → 运行前 override → 运行中控制台即时切。

04

技术方案

先校正设计文档的技术章节

文档 §6 的说法实测
新增 run↔session 绑定字段已有：session_id / present_in_session_id 早已在 WorkflowRun 上
新增 run 状态机（含 created）已有状态机；不引入 created——create_run 直接写 running，孤儿自愈已覆盖
新增 cancel / resume / rerun_fromcancel / resume / decide / retry / retry_from_checkpoint 都在；只有 rerun_from(node_id) 是新增
节点级 patch 走新端点不需要：前端合并 patch → PUT /workflows/{id} {dsl, commit} → 新版本。updateWorkflow 至今零调用者，正好启用
推送到观察台用「WS 或 SSE」本仓没有 SSE 基建，一律 WS；新增 /api/ws/runs/{run_id}
summarize 返回草稿需改造已是异步 draft-only（synthesis_id + 事件流），缺的只是 range 与「并入已有配方」
重写 workflows/engine.py 等多处编译器注入式改造 + 少量定点修改，不动 workflows/supervisor.py（它是校验失败恢复决策器，同名不同物）

运行状态与裁决动词

running ⇄ paused → done failed cancelled interrupted

paused 刻意不是终态（恢复即回 running）；终态是后四个。 在 paused 上可施加的裁决：继续 / 重试 / 跳过 / 改 context / 保持暂停 / 中止 —— 全部收敛到一条 POST /workflow_runs/{id}/decide。

Supervisor gate 插在哪里

gate 不是手写节点，而是编译期注入的合成节点：<N>__sup，插在 extract 注入之后 （有 <N>__extract 时挂在其后），把「继续 / 重试 / 跳过 / 中止」变成图上的条件边。 human 模式复用现成的 interrupt 通道——pending_interrupt 与 paused 机制一行不用改。

前端分解

新增 apps/web/src/components/workflow/studio/：StudioShell（三栏）、 StudioLeftRail + DecisionInbox、StudioCanvas（滚轮缩放 / 背景平移 / 节点拖拽落客户端 posOverrides，不引图库）、NodeInspector、 VersionsTab、RunObserver + useRunStream、 RunRightPane + SupervisorDecisionCard、SupervisorConsole、 ImportFromSessionModal、DevSessionDrawer。 布局算法从现有 WorkflowDag.tsx 抽成 canvasLayout.ts，WorkflowDag 改为 re-import，其它调用方行为不变。

约束应对
静态导出（output: "export"），全仓无 useSearchParamsStudio 选择态走 location.hash（#wf=&tab=&run=&node=）+ history.replaceState，不加动态路由段
ChatStream 是 AppShell 单例、跨路由常驻，不能二次挂载开发会话抽屉按 components/pin/PinStream.tsx 先例基于 blocks.tsx 自建
右 dock 只在 / 渲染，/workflows 上没有观察台建在页面内，不依赖 dock
现有 WorkflowInspector（558 行）还被 Settings 用着不拆掉，Studio 新写；版本抽屉等面板抽出去共用

06

权衡 · 不做 · 风险

维度评价
优势重流程 / 无头 / 定时运行体验最佳；可观测 + 可干预闭环完整；Supervisor 控制台天然落地；职责清晰
劣势轻对话用户要先学 Studio；「个人助手」的亲切感被工具感稀释；用户要在 Studio 与聊天两处之间跳
实现成本前端高（Studio 新建 + 画布交互 + 抽屉嵌对话）；后端中（五处定点新增）
主要风险对话体验被边缘化；画布交互边界易膨胀（已用「不做拖线建拓扑」锁住）

明确不做

  • 拖线建拓扑——已确认，节点参数在检查器改。
  • 新增 created 运行状态——现有「running 起步 + 孤儿自愈」已够，加了要动状态机与既有测试。
  • graph-aware cancel（取消后从 checkpoint 续跑）——取消仍是 task-kill；paused 本就能恢复，阶段 2 的 rerun_from 覆盖「继续一个已死的 run」。它自然接在阶段 2 之后，你要就加。
  • 不改 workflows/supervisor.py——那是校验失败恢复决策器，与本次 Supervisor 同名不同物。

最容易踩的地方

  • gate 注入会影响 _recursion_limit、run 的 steps 表、前端 BFS 分层——三处都要跟着改。
  • check_pause 是改动波及最广的路径（每个节点入口、每次工具迭代、每个并行项都调它），改前先跑它的专项测试。
  • FileCheckpointer.list() 产出的 config 里 checkpoint_ns 必须为空，否则 history fork 会断。
  • rerun_from 必须用 run 钉住的版本编译；版本被删则 409。
  • store 里 30 秒的兜底轮询在 WS 健康时不能重复取数。
  • 开发期一律 pnpm dev；make app 之后必须完全退出并重开 Ginno，否则必现 PyInstaller 懒加载的 zlib.error。

怎么验证

每阶段结束跑这三组；测试是 hermetic 的（隔离 $GINNO_HOME + 假 LLM，不联网）。

cd packages/runtime
./scripts/test.sh -m unit -k workflow      # 单测
./scripts/test.sh -m api -k workflow       # 接口
./scripts/test.sh                          # 全量（当前基线：后端 692 通过）

pnpm --filter @ginno/web typecheck && pnpm --filter @ginno/web lint
pnpm dev                                   # web:3000 + runtime:8787，源码直跑

端到端手验项：观察台的推送在浏览器 network 面板可见（不是 1.5s 轮询）；杀掉 sidecar 重启后重连能重放； tests/e2e/test_session_workflow_lifecycle.py 每个阶段保持通过。
