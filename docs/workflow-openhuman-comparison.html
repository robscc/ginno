00摘要

四路独立调研（Ginno 产品/技术 × 本地仓库全量文档与代码；OpenHuman × 浅克隆代码级深读；tinyflows × 引擎源码级深读）后的核心判断：

  • 理念同源，路线分叉。两者都收敛到「agent 提议自动化 → 人审阅 → 批准后才生效」，且都把「批准」做成结构性机制而非提示词约定。分叉在媒介：Ginno 选择对话优先（明确不做画布编辑器，DSL + diff 卡为载体）；OpenHuman 选择画布优先（React Flow 可视化 + 内嵌 copilot，叙事对标 n8n/Zapier）。
  • Ginno 的长板：会话蒸馏创建（summarize-from-session 提炼的是真实用法而非想象中的自动化）、总结质量漏斗度量体系（L0–L4 + case 档案 + replay，OpenHuman 没有对应物）、doctor 运行前静态检查、运行回到对话的内联体验、浏览器一等节点。
  • OpenHuman 的长板：触发器体系（cron/应用事件/手动/恢复 + 启动重注册 + per-flow 并发锁）与无人值守安全工程（trust origin、服务端强制规则、预授权清单、graph_hash 防过期审批）——这恰是 Ginno 的两个最大缺口。
  • 引擎层面 tinyflows 表达力明显更强（并行扇出、错误路由、retry/backoff、子流程、dedup、spawn/gate），但两者共享同一血统——都是 LangGraph 风格超步运行时 + checkpoint + interrupt/resume；Ginno 直接用 LangGraph Python，tinyflows 是从 tinyagents vendored 的裁剪版 Rust 运行时。
  • 最值得借鉴的不是画布，而是：① 结构性安全闸门（若 Ginno 要做定时/无头运行，这是前置条件）；② Fix-with-agent 失败修复闭环；③ 全链路白话化；④ 模板 + 主动发现（Scout）；⑤ dry-run 提速。画布编辑投入巨大（OpenHuman 自评「最大 UI 工程」），与 Ginno 的团队规模和哲学不匹配。
  • 成熟度：两者 workflow 都在 1.0 之前。OpenHuman 面更大但挂 Beta 横幅、webhook 未实现、存在文档/代码不一致（审批 TTL）；Ginno 面更小但计划内事项全部落地（692 测试通过），质量度量机制反而领先。

02产品定位：两种哲学

Ginno
对话领先，流程跟随
「先聊出结果，再把过程固化；运行时也回到对话里观察，而不是被甩到一个独立页面。流程不是被打开的页面，而是对话的另一个视角。」docs/design/session-workflow-A.md §1

workflow 是会话的结构化投影 / 可重放脚本：把「重复发生的、步骤已知的多 Agent 任务」固化成版本化 DSL 配方，确定性重放。产品内三分法清晰：TODO 回答「要做什么」、Workflow 回答「怎么做（已知流程）」、Goal 回答「达成什么（开放目标）」。

来源：workflow-dsl-design.md 开篇、goal-design.md §3.1

OpenHuman
把重复工作放上自动驾驶
「Chat is great for one-off asks. Workflows are for the things you want done every time… Heavily inspired by n8n and Zapier… The difference: you don't build the graph, the agent does.」gitbooks/features/workflows.md

workflow 是无人值守的自动驾驶：定时、事件触发、重启存活、副作用经审批。竞品对比表中四个形容词就是产品主张——「Visual, durable, agent-proposed, approval-gated」。欢迎页文案：“Put the busywork on autopilot.”

来源：README「Workflows you can see」、FlowsPage 欢迎页

判断　定位差异是后面一切差异的根：Ginno 的 workflow 服务于「把这次好用的对话变成下次可重放的脚本」，所以入口在聊天页、运行回对话、不需要触发器；OpenHuman 的 workflow 服务于「我不在场它也按时干完」，所以必须有触发器、审批闸与持久化。两者不是优劣，是场景排序不同——但 Ginno 的文档自己也承认，无头/定时运行是开放问题（方案 A 契合度仅 ★★，方案 B 工作室路线 ★★★★★）。

3.2 编辑：对话 + diff 卡 vs 画布 + copilot

Ginno
刻意不做画布编辑器
「所有修改前后对比确认 + 版本化由独立 interrupt + diff 卡天然保证，且不需要任何 DAG 拖拽编辑器。」workflow-dsl-design.md §8.3；user-guide §9.5 标题即「对话式编辑（无 DAG 拖拽编辑器）」
  • 修改路径：workflow-dev agent → propose_edit → violet diff 确认卡 → Apply 才落新版本
  • 版本不可变快照 + VersionHistoryDrawer + 任意两版 diff + 回滚
  • doctor 静态 lint（无来源变量/路径字面量/未消费 writes）+ 一键升级
  • DAG 只读：状态着色、实时高亮、点节点过滤日志
OpenHuman
画布是一等公民，但创作主线仍是 agent
  • React Flow v12：拖拽连线、删除、undo/redo、节点面板（16 项三组）、form ⟷ JSON 双模检查器、cron 白话编辑器
  • Copilot 面板与画布并存：提议到达时进入 diff 审阅态——新增节点 sage 实线环、删除节点 45% 透明「幽灵化」，Accept & save 才落库
  • 防抖 500ms 自动 flows_validate，错误阻断保存、警告不阻断
  • 刻意不做自动保存（注释：saved+enabled 即 live，误存会真的触发 schedule），每次保存有确认弹窗 + 离开守卫
  • 20 版修订历史 + rollback；支持 n8n JSON 导入

分析：表面上是「无画布 vs 有画布」，实质两边的编辑主叙事都是 agent 提议 + diff 审阅——OpenHuman 的规划文档明写「手动画布是 escape hatch, not the headline，两条创作路径在文案上不许互相竞争」。差异在兜底手段：OpenHuman 给 power user 直接操作的能力（规划文档称画布是其「最大 UI 工程」），Ginno 用 doctor + dev 会话 + 原始 JSON 兜底。Ginno 的取舍省下了巨大的 UI 维护面，代价是空间式理解与细粒度手动调整能力弱。

3.5 审批与人机协作：哲学相反，但会在「无人值守」处汇合

Ginno · 自由侧
「人在环上而非环内」
  • 默认自主跑（bypass）；permission 子系统计划全局移除
  • 四类 interrupt：human 问答、手动暂停、浏览器交接、DSL diff 确认——统一走 LangGraph interrupt + checkpoint
  • 安全底线 = 路径硬 deny（~/.ssh、Keychains、~/.ginno）+ 越界 tool error
  • workflow 步骤强制剥离 workflow_* 工具防嵌套；tools_allow 按 agent 过滤
OpenHuman · 控制侧
四层审批工程
  • 信任模型：flow run 有专属 trust origin；静态图配置 = 保存时已审 = 可信，运行时事件载荷 = 不可信、只能喂参数不能引入新动作
  • 服务端铁律 B29（与 UI/agent 无关）：自动触发图强制 disabled 落库；含出站副作用节点强制 require_approval
  • 预授权清单：启用时一次性展示「这个 flow 会要哪些权限」，四类诚实文案（approvable / blocked / dynamic / agent），信任按 (flow_id, tool) 粒度存，绝不全局放行
  • 运行中 gate：Approve once / always（限本 flow）；park 时钉住 graph_hash，图被改过则拒绝恢复（防过期审批）；无人应答 600s fail-closed 取消
判断　交互式会话里 Ginno 的「自由」是对的——审批疲劳是真实成本。但这条哲学直接平移到无人值守运行会出问题：一个定时跑、能发邮件、能写文件的流程，「默认 bypass」等于把钥匙留在门上。OpenHuman 给出的答案不是「处处审批」，而是把信任边界前移到保存/启用时刻（图是审过的、权限是一次性批量授予的、信任按 flow 隔离），运行时只在未预授权处停。这套机制与 Ginno 的交互式自由可以共存：交互会话保持 bypass，自动触发的 flow 走闸门轨道。

04技术方案对比

4.1 图格式与数据模型：黑板 vs 流水线

两者都是 JSON 图（nodes + edges），但数据如何流动是根本分歧：

Ginno · 共享 Context 黑板 
{
  "dsl_version": "1",
  "entry": "fetch",
  "context": {            // 一等公民：schema + 初值 + 来源追踪
    "schema": {"type":"object","properties":{
      "repo":{"type":"string"},
      "prs":{"type":"array","items":{"type":"object"}}}},
    "initial": {"repo": "robscc/ginno"}
  },
  "nodes": [
    {"id":"fetch","type":"step","agent":"research",
     "goal":"列出 {{context.repo}} 的待审 PR",
     "writes":{"prs":{"type":"array","items":{"type":"object"}}}},
    {"id":"each","type":"loop","over":"context.prs",
     "as":"pr","body":"review","max_iters":50},
    {"id":"gate","type":"branch","cases":[
      {"when":"len(context.drafts) > 0","then":"notify"}],
     "default":"done"}
  ],
  "edges": [{"from":"fetch","to":"each"}]
}

步骤间靠命名 context 键传值；writes 是硬契约（编译器注入 extract 节点保证产出）；context_meta 追踪每个值来自 initial/step/human。表达式是自研 Python AST 沙箱（白名单、禁 dunder、≤4000 字符/300 节点，防 LLM 病态输入）。

tinyflows · Item 流水线（n8n 风格） 
{
  "schema_version": 1,
  "inputs": [{"name":"repo","type":"string","required":true}],
  "nodes": [
    {"id":"start","kind":"trigger",
     "config":{"trigger_kind":"schedule","schedule":"0 9 * * *"}},
    {"id":"fetch","kind":"http_request",
     "config":{"method":"GET","url":"=inputs.repo"}},
    {"id":"each","kind":"split_out","config":{"path":"result"}},
    {"id":"work","kind":"agent","config":{"prompt":"Review",
     "execution":"per_item","concurrency":8}},
    {"id":"gate","kind":"condition",
     "config":{"field":"=item.json.priority == \"urgent\""}}
  ],
  "edges": [
    {"from_node":"gate","from_port":"true",
     "to_node":"notify","to_port":"main"}
  ]
}

连接上流动的是 Item 数组（{json, binary?, paired_item?}）；每节点写自己的输出槽，跨层引用 =nodes.<id>.item.x；分支标签写在边的 from_port 上。表达式是 = 前缀 + jaq/jq 全量（剔除 env 等危险内建），null 解析会被追踪诊断。

分析：Ginno 的黑板模型更贴 LLM 工作流——步骤是「达成 goal」，产出是命名数据，doctor 能静态验证「每个引用都有来源」；代价是没有按 item 的天然并行。tinyflows 的 item 流更贴集成自动化——per_item 扇出、dedup、scatter/gather 都是数据驱动宽度；代价是全局可变上下文与「步骤产出命名键」这类 LLM 友好抽象要自己搭。Ginno 若做 v2 并行，tinyflows 的「输出恒按输入顺序 + paired_item」确定性承诺值得直接抄。

4.2 执行引擎：同一血统，不同完成度

一个有趣的事实：两者都是 LangGraph 风格超步运行时——Ginno 直接使用 LangGraph Python；tinyflows 的 src/graph/ 是从姊妹 crate tinyagents vendored 并裁剪的 LangGraph 风格运行时（超步、reducer、command/interrupt、checkpoint、streaming）。执行语义因此高度同构：superstep 边界提交 checkpoint；interrupt 暂停；被中断节点恢复时从头重跑（at-least-once）。

06借鉴清单：OpenHuman 产品设计思路 → Ginno 行动

先提炼设计思路（6.1），再按落地成本分层的行动清单（6.2–6.4）。

6.1 OpenHuman 值得内化的七条设计思路

  1. 结构性保证 > 提示词约定。「agent 提议、人来保存」靠五道闸门实现，其中四道在后端：propose 工具永不落库、builder 工具表里不存在 enable 工具、create/duplicate 永远 born disabled、自动触发图服务端强制 disabled、出站副作用强制审批——与 UI/agent 是否守规矩无关。Ginno 已有同款思想（「writes 是硬契约」「retry 永远是手动」），可把该思路推广到未来的无人值守场景。
  2. 提议权与落库权分离。agent 只能产出「建议」，落库动作永远由 app 代用户发起。Ginno 的 summarize 草稿已符合；version_propose 已符合；未来任何 agent 可触发的新动作面（如 agent 建议定时任务）都应继承这条。
  3. 权限最小化 + 诚实标注未知。预授权清单把条目分成 approvable / blocked / dynamic（运行时才知道）/ agent（AI 步骤内部不可枚举）四类，对无法预知的部分诚实说明而不是假装全知。Ginno 的 doctor 警告与运行错误文案可借鉴这种「分级 + 诚实」表达。
  4. 全链路白话化。节点类型人性化（future_thing → “Future thing”）、cron 白话摘要、步骤结果白话（“Fetched 3 item(s)”）、运行失败与配置错误用两种红色。画布给非技术用户看的是人话不是 slug。Ginno UI 目前偏工程语汇（事件 kind、DSL 术语）。
  5. 克制：推荐系统只给提议权。Flow Scout 的 Build this 只是把建议预填进输入框，绝不自动发送；「真实试运行必须用户明确确认」。主动性与控制权的边界画得很清楚。
  6. 把设计理由写进代码注释。「不做自动保存」的原因（saved+enabled 即 live）直接写在注释里；「Identity is a filled square; status is an outline」的视觉原则写在组件里。Ginno 的 implementation-notes 文化已经更好——保持。
  7. fail-closed 的保守默认。审批无人应答 10 分钟即取消（代价是文档叙事没跟上，成为反面教材）。无人值守场景里，保守默认 + 明确文案优于宽松默认 + 静默。

6.2 第一层：低成本高回报（可立即排期）

01Fix-with-agent 失败修复闭环成本低体验收益高

OpenHuman：failed run 上一键把错误 + 失败节点 id 喂给画布 copilot 发起 repair turn，审阅-修复不断出画布。Ginno 的零件全在（RunErrorBox、workflow-dev 会话、doctor、error_detail 归因），只差一根线。

落地　RunErrorBox 增「让 dev agent 修复」按钮 → newSession(workflow-dev) 并注入 seed：workflow 名 + 当前 DSL + 失败节点 id + error + 相关事件片段。修复走既有 propose_edit diff 卡。
02全链路白话化 + 两种红色成本低

把事件 kind、节点类型、错误信息转成人话；「运行失败」与「DSL 配置错误」用不同视觉（对应 Ginno 的 run error vs doctor error），避免用户误诊。

落地　时间线/步骤列表/通知文案统一过一层 humanize 映射；doctor 面板与 RunErrorBox 配色区分；stuck 通知已有基础，补齐其余触点。
03version_propose 可视化 DAG diff成本中低

OpenHuman copilot 的 diff overlay（新增节点实线环、删除节点幽灵化 + 计数徽章）比纯文本 unified diff 直觉得多。Ginno 已有 WorkflowDag 组件与 canonical diff 数据。

落地　diff 确认卡在文本 diff 之上加一个小型 DAG：对 current 与 proposed 两版图做节点 id 对齐，新增=绿环 / 删除=半透明 / 变更=标记。文本 diff 保留为展开详情。
04dry-run 提前（原 P2）成本中低安全收益

OpenHuman 的 dry_run_workflow 用 mock capabilities 跑草稿图，零副作用、不设自治门槛（只读 agent 也能自检提议），并且「真实试运行必须用户确认」。Ginno tooling-plan 已规划（step/llm 替换为回显 stub），可提级：它同时是总结质量工具（L3 前置验证）与未来无人值守的安全件。

落地　按既有设计实现 stub 编译路径；在 SummarizeModal 与 doctor 面板暴露「试运行」；dev agent 允许自主 dry-run、禁止自主真跑（对齐 OpenHuman 的工具带设计）。

6.3 第二层：与触发器演进绑定的战略件

这一层是一个包：触发器 + 无人值守安全 + 引擎容错必须成对引入。只做触发器不做闸门 = 造出没人看管的副作用机器；只做闸门没有触发器 = 闸门无用武之地。

05触发器体系（schedule / event）最大缺口成本中高

OpenHuman：trigger 是 DSL 的一等字段（cron/at/every），启用时注册调度作业，每次 app 启动幂等重注册（“survive restarts” 的真实含义），per-flow in-flight 锁防定时突发并发，触发只发事件、dispatch 前复核 enabled。这是「autopilot」叙事的地基。

落地　DSL 增 trigger 段（kind: manual/schedule/event）；runtime 加轻量调度器（启动重注册 + 事件复核 + per-flow 锁）；事件类先做 Ginno 内部事件（todo/goal/kb 变更）再接外部（webhook 可缓，OpenHuman 自己也没做完）。
06无人值守安全闸门（B29 模式）与 #05 绑定成本中

OpenHuman 的四层里，Ginno 至少需要三层的对应物：
① 服务端铁律：自动触发的 workflow 强制 born disabled，需显式启用；含出站副作用（发通知/写外部平台/HTTP）的 DSL 强制开启审批或至少显式确认——这两条与 UI/agent 无关；
② 启用时预授权清单：一次性说清「这个 flow 会动什么」（工具/路径/外发），信任按 (workflow, tool) 粒度记录，文案对未知项诚实（dynamic/agent 分类）；
③ graph_hash 防过期审批：run 停在审批时钉住 DSL 版本，恢复前校验图未变，变了就拒绝并给专属文案。Ginno run 已钉 dsl_version，补校验即成。

落地　复用现有 interrupt 通道增一种 nature（automation_gate）；信任表可落 ~/.ginno/workflows/<id>/trust.json；与「permission 全局移除」方向不冲突——交互会话保持自由，闸门只作用于自动触发的 flow。
07引擎级 retry/backoff + on_error 路由成本中无人值守基本件

tinyflows 每节点可配 retry（max_attempts + fixed/exponential 退避）与 on_error（stop/continue/route）；Ginno 目前失败即终态、全靠人手动重试——「Retry is always deliberate」在交互场景是美德，在凌晨三点的定时任务里是事故。另建议 per-node 超时配置（现全局 300s）。

落地　DSL step/agent 节点加 retry/on_error 可选字段，默认保守（不重试）；副作用类节点重试需配合幂等提示（doctor 增规则：有外发工具的节点开重试时 warn）。

6.4 第三层：长线选项

08模板库 + Session Scout（主动发现）成本中Ginno 特色机会

模板便宜（把 pr-triage 之外再沉淀 3–5 个 JSON，放进创建入口）。Scout 更有趣：OpenHuman 靠行为遥测建议自动化，而 Ginno 手里有更好的材料——synthesis case 库已经记录了每次会话蒸馏的采用/丢弃/首跑结果。「你最近三次会话都在做类似的事，要不要固化成流程？」是从真实用法长出来的建议，与「对话领先」哲学完全自洽。记住克制原则：只提议、只预填，不代办。

09flow 私有记忆命名空间成本中

OpenHuman 每个 flow 有私有 memory namespace：成功 run 的 ≤1000 字摘要自动沉淀（上限 50 条），下次运行的 agent 步骤可读「上次跑发生了什么」；dedup 节点还靠它做跨 run 去重、且只在 run 成功后 commit。这让重复性自动化有「经验积累」。Ginno 的记忆系统现成，接一根管即可。

10节点契约 catalog 反哺生成质量成本低直击 L1 失败

Ginno 节点注册表已有 params/inputs/outputs schema；把它们整理成机器可读契约（每类型：字段/约束/示例/常见错误），注入 summarize 与 workflow-dev 的提示词。synthesis 失败标签中 schema 类占大头——这是用 tinyflows 的「agent-first catalog」思路打 Ginno 自己的 L1 漏斗。

11战略议题：画布要不要做建议：暂缓，但升级观察台

OpenHuman 的证据表明画布与 agent 创作并不互斥——它的创作主线仍是 agent 提议，画布承担「观察台 + escape hatch」，且即便如此仍被其自评列为最大 UI 工程。Ginno 现有立场（无拖拽编辑器）在团队规模下依然成立；建议的中间路线是：保持对话编辑主线，把只读 DAG 升级为更强的运行观察台（实时 overlay + 点选下钻 + §03 的可视化 diff），拿到画布八成的理解力、不背两成的编辑维护成本。若未来数据表明「复杂图编辑往返成本」成为采用漏斗的瓶颈（L2 heavy_edit 标签），再重议。

07反向观察：Ginno 的独有价值与 OpenHuman 的镜鉴

借鉴不等于仰望。调研同样揭示了 Ginno 不该丢的东西，和 OpenHuman 踩过的坑：

Ginno 独有 / 领先
  • summarize-from-session：从真实会话蒸馏工作流——OpenHuman 的 propose 来自用户口头描述，起点信息量更低
  • L0–L4 质量漏斗 + case 档案 + replay：生成质量的度量与 A/B 基建，OpenHuman 无对应物
  • doctor 运行前静态检查（tinyflows 的 gates 同思路但更偏结构合法性，Ginno 做到了数据流来源分析）
  • 运行回到对话（run.bind 内联）：监控的「就近原则」做得比 hub 式产品更彻底
  • 浏览器一等节点 + 登录交接：OpenHuman 需要 Chrome 扩展 companion 才覆盖同等场景
  • context 来源追踪（context_meta）：「这个值哪来的」在 item 流模型里要靠 null 诊断反推
  • 文档/实现对账文化：implementation-notes 逐条记录偏离与事故，OpenHuman 出现了文档领先代码的情况
OpenHuman 的坑（镜鉴）
  • 文档/代码不一致：gitbook 说审批暂停「later today is fine」，代码是 600s TTL fail-closed 取消——保守实现没错，叙事没跟上就是信任损耗
  • webhook 触发声明了没实现：能力宣称与实际面要有明确边界（Beta 横幅是好习惯）
  • 审批 UX 复杂度高：预授权 + once/always + gate 卡片两代并存，学习成本不小——闸门多寡要与场景匹配
  • 画布轮询 2s：Run Inspector 靠 live-polling 而非推送（Ginno 的 WS 推送更优）
  • 画布工程成本：其规划文档自认 Phase 3 画布是「最大 UI 工程」——Ginno 不跟是对的，除非数据说话

08结论

一句话：Ginno 与 OpenHuman 在「agent 起草、人批准」上殊途同归，在「对话 vs 画布」上各押一边；Ginno 赢在起点质量与质量度量，OpenHuman 赢在触发面与无人值守安全工程。

三个真实差距（按重要性）：① 触发器 + 无人值守安全机制（战略缺口，成对补齐）；② 引擎容错语汇（retry/on_error，无人值守基本件）；③ 失败修复闭环与白话化（体验打磨，成本低）。

三个不要跟：全功能画布编辑器（成本与哲学都不匹配，升级只读观察台即可）；审批复杂度向交互会话蔓延（闸门只加在自动触发轨道）；能力宣称跑在实现前面（OpenHuman 的 TTL 教训）。

行动序：先做第一层四件（Fix-with-agent / 白话化 / DAG diff / dry-run）——两周内可见效且不动架构；随后把「触发器 + B29 闸门 + retry」作为一个设计包整体评审（这是 Ginno workflow 从「重放脚本」到「值班员工」的成人礼）；Scout、flow 记忆、节点契约 catalog 按质量漏斗数据择机插入。

A.5 边与数据适配

Ginno 边 = 连接 + 适配器 
{"from":"fetch","to":"each",
 "transform":{
   "map":  {"repo":"prs[0].repo"},   // 路径复制
   "expr": {"n":"len(context.prs)"}, // 沙箱表达式
   "pick": ["title"],                // 只带这些键
   "defaults": {"lang":"zh"},
   "fn":   "my_registered_xform"     // 注册自定义
 }}

无 transform 时默认 = context 浅合并上游 output。结构性禁令：branch 不得有显式出边；loop body 的回边是结构边、不许手写。

tinyflows 边 = 纯端口连接 
{"from_node":"gate","from_port":"true",
 "to_node":"notify","to_port":"main"}

数据适配不在边上：整形用 transform 节点（set:{k:"=expr"}）或下游 = 表达式自取。分支标签必须在 from_port（HARD RULE）；多前驱节点自动接 fan-in 屏障（merge 语义）。

分析：Ginno 把适配放在边上是务实的——LLM 起草时「把上一步的 X 作为下一步的 Y」是一句话的事；代价是边变「胖」、校验更复杂。tinyflows 的边保持极简，把适配推给节点与表达式，换来端口/屏障/扇出的统一语义。两者都做了「路由写错位置即验证失败」的硬规则，只是落点不同。

  • 顶层 trigger 段：不必学 tinyflows 做成节点；Ginno 的 entry 已独立，加 "trigger":{"kind":"schedule","cron":"0 8 * * 1-5"} 顶层对象更贴现有形状（与 §6.3-05 绑定）
  • 每节点 retry / on_error / timeout_s：无人值守基本件；默认保守（不重试）
  • type_version 双轴迁移：现在只有 dsl_version 单轴，某 kind 的 config 形状一旦调整就会撞旧版本；学 tinyflows「per-kind 版本 + 加载期迁移 + 过新拒绝」
  • void 语义：把「副作用终点、无人等待」写进类型（比 pass 更诚实），配合未来 spawn 式异步触发
  • 节点契约 catalog：注册表里的 params/inputs/outputs schema 整理成可枚举契约，注入生成侧（打 L1 漏斗）
应当保留（Ginno 更优处）
  • context 黑板三件套（schema 驱动 UI 表单 / initial 默认输入 / meta 来源追踪）——tinyflows 没有对等物，「这个值哪来的」要靠诊断反推
  • writes 硬契约 + extract 注入——比 output_parser 的「作者自觉」强一个量级；事故证明过
  • {{}} 散文模板——goal 可读性是对话式产品的门面；tinyflows 无插值是真实痛点
  • 结构性路由禁令（branch/loop-body 禁显式出边）——与 tinyflows 的端口硬规则等效但更省认知
  • 保留后缀等防碰撞规则 与 canonical_dsl 版本 diff——工程纪律的体现
  • loop 空序列显式化（on_empty + loop_skip 事件）——tinyflows 的 split_out 空数组至今静默，Ginno 在这里是领先的，别在借鉴时弄丢
结语　两份 DSL 是两种产品哲学的精确投影：Ginno 为「LLM 起草 + 人确认 + 对话执行」优化（散文 goal、黑板 context、硬契约 writes），tinyflows 为「宿主无关 + 确定性流水线 + agent 可调试」优化（端口边、item 流、契约 catalog、testkit）。互译练习表明它们并非不可通约——控制流概念一一对应，真正不可通约的是数据模型（黑板 vs item 流）与触发/容错字段的存在性。Ginno 的演进不必换数据模型，而应把 tinyflows 的「触发、容错、版本迁移、契约」四个字段族移植进自己的黑板模型——用最小语义变动补齐无人值守所需的全部表达力。
