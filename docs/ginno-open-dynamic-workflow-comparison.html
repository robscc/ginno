GINNO 对比研究 · 第三篇

Ginno × Open Dynamic Workflow

travisliu/open-dynamic-workflow 是一个本地优先的一次性编排脚本运行器,把外部编码代理 CLI 统一成可测试、可复现的工作流原语。本报告逐维度对账,给出分层借鉴清单。

调研日期 2026-10-12 对象 github.com/travisliu/open-dynamic-workflow(README / SKILL.md / api-document / cli-commands / configuration 五份文档级调研) 前序 OpenHuman(2026-08-16)、DeepSeek Harness(2026-08-30) 状态 调研完成,未实施

01一句话结论

这是「workflow」同名不同种的第三个数据点(OpenHuman 画布引擎 → dsh 一次性脚本 → ODW 确定性重放运行器),再次验证此前结论:持久化轴上 Ginno 领先,不需要动摇方向。ODW 真正值钱的不是它的 DSL,而是围绕「可复现性」做的三件事——指纹前缀重放的跨 run 结果缓存、per-step 独立产物目录、确定性冒烟(mock provider)——恰好都补在 Ginno 的空档上。另有预算闸门与 secret 脱敏两个安全/成本短板可低成本补齐。Ginno 的人审、合成、版本化、调度等资产 ODW 全部没有且明确声明不做。

02项目画像:Open Dynamic Workflow 是什么

TypeScript 编写的本地 CLI 运行器(npm 包 @travisliu/open-dynamic-workflow),MIT,2026 年开仓,84 stars / 148 commits,单人项目。定位是「agent 编排版的工作流引擎」——不自研 agent,通过 provider 适配器调外部编码代理 CLI。

核心机制

  • DSL = 受限 TS 脚本:六个原语 agent() / parallel() / pipeline() / workflow()(子工作流) / loop() / tool(),沙箱化——禁止任意 import、fs、网络、shell
  • 8 家 provider 适配器:codex / gemini / copilot / opencode / antigravity / pi / cursor / mock(确定性干跑),config.yaml 可自定义 command/args
  • 确定性重放 resume:重跑时从头执行脚本,每个 agent 调用按指纹(id+prompt+schema+provider+model+retry 策略)与上次 run 前缀比对,命中即复用缓存结果,首个分歧之后全部实跑
  • Artifacts 恒开:每次 run 落 runs/<runId>/,含 manifest / calls.jsonl / events.jsonl / report.json + 每个 agent 的独立目录(prompt、stdout/stderr、raw/normalized 结果、schema、validation-error)
  • 结构化输出:JSON Schema + transport(prompt 注入 + 本地验证),验证失败可作为带反馈的重试依据

工程与安全

  • 默认值纪律:concurrency 4、timeout 900s、maxLoopRounds 20、maxDepth 8、retry(exponential, 3 attempts, 30s cap, jitter)
  • 预算闸门:maxAgentCalls 限制活跃 provider 调用数,含重试尝试
  • secret 卫生:redactEnv 默认脱敏 *_KEY / *_TOKEN / *_SECRET / PASSWORD 等;passEnv 默认空白名单;doctor 不打印 secret
  • profiles:继承式执行预设(fast/deep),字段安全白名单,禁止改 provider command 与安全策略
  • SKILL.md 教 AI 写/审工作流:11 步生成流程 + Critical/High/Medium/Low 评审清单 + 四段式输出模板(workflow / how to run / design notes / validation checklist)
  • 明确不做持久化、审批门、DAG、worktree 隔离、分布式、可恢复运行状态(见 §6)

04可借鉴清单(分层)

P1 可立即排期低成本、补真实空档;P2 值得排期中等成本、明确收益;P3 远期;每项标注 Ginno 侧落点。

P1① 跨 run step 结果缓存:指纹前缀重放

ODW 的招牌机制。重跑 = 从头执行 + 逐节点指纹比对,前缀命中复用上次结果,首个分歧节点之后实跑。指纹 = (节点稳定 id, prompt, writes schema, model, retry 策略)。它把「改了一处、整个 workflow 重跑烧钱」变成「只有分歧下游实跑」——直接强化三类场景:失败修复(修好一个坏节点后重跑,上游全部命中缓存)、L0-L4 评测回放(换一个节点的模型/prompt 做对比)、synth 迭代。Ginno 的基础全在:节点本来就有稳定 id,run JSON 已有 per-step output,唯一要建的是指纹规则 + 缓存索引 + 「复用结果」的事件标记(重放结果需在 UI/events 中显式标注,不能伪装成实跑)。

落点:workflows/store.py(run JSON 旁加 cache-index)、engine.py(节点进入前查缓存)、nodes/builtin.py(prompt 组装处取指纹)。注意:Python 节点/含工具调用的 agent 节点默认不参与缓存,只对纯 LLM step 开放,避免重放副作用——ODW 用「tool 结果也缓存」解决此问题,可作二期。

P1② secret 脱敏层:redactEnv + passEnv 白名单

Ginno workflow 模块目前没有任何 secret 卫生机制:context_override 全文落盘 run JSON,agent step 的工具输出原样进 events.jsonl,delegate_agent 子进程继承全量 env。ODW 的做法很轻:默认脱敏 *_KEY/*_TOKEN/*_SECRET/PASSWORD,passEnv 默认空白名单(白名单内的才传给子进程)。至少应覆盖三处:run JSON/events 落盘前的值级脱敏、delegate_agent 的 env 传递、doctor/inspector 的展示层。

落点:workflows/store.py(序列化前过滤)、tools/external_agent.py(子进程 env 构造)、新增一个 workflows/redact.py 单一事实源。

P1③ 预算闸门:maxAgentCalls(含重试)+ run 级并发上限

Ginno 有 recursion_limit 但没有「活跃 LLM 调用数预算」。maxAgentCalls 的语义好在把重试尝试也计入——retry 放大了成本失控面,只数首次调用是不够的。调度触发的 headless run(无人值守)尤其需要这个闸门,呼应 OpenHuman 报告的「无人值守安全闸门」结论。run 级并发上限同理:多 run 并行时目前无全局节流。

落点:workflows/engine.py(预算计数器,与 recursion 预算并列)、nodes/agent_helpers.py(record 处挂计数)、DSL 根级 limits{max_llm_calls, max_concurrency}。

P2④ mock/stub 模型 provider:确定性全流程冒烟

Ginno 的 dry-run 是零 LLM 静态检查,不执行;单测里有 fake model 但无法从产品面跑通整张图。ODW 的 mock provider 能把整条 workflow 用确定性桩模型真跑一遍,并作为 init 冒烟测试与 CI 示例的默认。对 Ginno 的直接价值:e2e/UI 测试从「假模型 + 单测」升级为「真实引擎全链路冒烟」;将来建最小 CI(dsh 借鉴清单 #2)时,workflow 冒烟可以是第一条门禁。stub 规则可以很简单:按节点 id/序号回放录制的响应,或命中 writes schema 的最小合法 JSON。

落点:nodes/base.py(模型工厂加 stub 实现)、run API 加 stub: true 参数(仅 dev 模式暴露,防止生产误用)。

P2⑤ workflow-dev prompt 吸收 SKILL.md 的评审纪律

ODW 给「AI 写工作流」定了一套机器可检查的纪律:生成走 11 步(澄清→选模式→先写 meta→只用原语→provider 有理由→schema→权限最小化→显式并发/失败行为→先 validate 后 run→按清单终审→四段式输出),评审按 Critical/High/Medium/Low 出 findings。Ginno 的 workflow-dev prompt(图模式 + dry-run 预检)方向一致但缺结构化评审输出。低成本改法:在 workflow_propose_edit 的提示词中加一张固定评审清单(node id 稳定性、loop 有界、on_error 显式、权限最小、无未声明写入),让 agent 的每次提案自带 findings——正好也是 quality funnel L1-L2 的输入。

落点:tools/workflow_tools.py(propose_edit prompt)、docs/workflow-master-plan.md(质量漏斗对账)。

P2⑥ per-step 独立产物目录(normalized 结果 + 验证错误分文件)

Ginno 的 events.jsonl + transcript 镜像信息完备,但调试单个坏 step 要靠回放拼接;ODW 把每个 agent 的 prompt / raw / normalized / schema / validation-error 分文件落盘,「schema 校验为什么失败」一眼可见。对 Ginno 的取舍:不必照搬全量,只在失败 step + extract 自纠错耗尽的节点落独立目录(原始回复、抽取结果、校验错误三件套),UI 的 WorkflowInspector 加「查看原始输出」入口。成本小,把最痛的调试场景(抽取/校验失败)从考古变成看文件。

落点:workflows/nodes/extract.py(自纠错耗尽处落盘)、store.py(run 目录布局)、前端 Inspector。

P3⑦ profiles 执行预设(质量档位)

ODW 的 profile = 继承式预设(fast/deep:换模型、改并发、收紧 retry),字段白名单防越权,运行时注入 hash 元数据保证可追溯。对 Ginno 的映射是「同一 workflow 按档位执行」——schedule 无人值守跑 fast 档、人工触发跑 deep 档。当前 agent 角色承担了部分职责,若 ①③ 落地后出现「按场景换全局参数」的真实需求再做不迟。

落点:DSL 根级 profile 字段 + meta.json 预设表(远期)。

05明确不跟

  • TS 脚本 DSL 与六原语组合——ODW 用 promise 组合替代图结构,证明了「结构化原语可以不开自由 DAG 就表达 fan-out/fan-in」(parallel() + 汇总节点)。这对 Ginno 是个反向确认:现有 linear + 并行 loop 的受控结构够了,不需要为 DAG fan-out 推翻 DSL;真需要扇出时,优先学它的「结构化原语」思路扩展 loop/branch 语义,而不是开放任意边。
  • 8 家 CLI 适配器矩阵——Ginno 的 delegate_agent 刻意只做 claude-code/codex 双后端(dsh 报告与 external-agents-design 的裁定),适配器矩阵是平台玩法,且 ODW 自己也承认 transport native 至今被所有 adapter 拒绝——适配层越宽,统一抽象越浅。
  • 无持久化哲学——「一次性脚本 + 全量 artifacts 事后可查」是刻意的简单性,Ginno 的业务流程引擎(人审、定时、修复闭环)必须持久化,不适用。
  • maxRounds 硬顶替代引擎兜底——ODW 把无限循环防护完全交给静态上限(全局 maxLoopRounds=20);Ginno 的 recursion 预算 + supervisor 已覆盖,无需改。
  • 分享 runs 产物的模式——ODW 自己警告 artifacts 含 prompt 与源码片段;Ginno 若做「导出/分享 run」,必须先过 ② 的脱敏层。

06Ginno 独有资产(ODW 明确不做或没有)

ODW README 明示「不得假设存在」的

  • 持久化状态与可恢复运行(ODW:一次性)
  • 审批门 / human-in-the-loop(ODW:无)
  • worktree / 容器隔离、分布式执行
  • 自动打补丁/提交/合并的默认行为

ODW 生态位之外、Ginno 已有的

  • checkpoint/resume/pause 全套 + DSL 版本化 diff 审批
  • 会话 → workflow 合成(synth-5)+ outcome 回填台账
  • scheduler 定时触发 headless run(双方都还没有事件触发器,仍是共同空档)
  • supervisor 裁决器、decision inbox、quality funnel L0-L4
  • run 会话镜像回到对话、run 全 UI 集成

07附录:ODW 关键机制细节(供实施时参照)

指纹前缀重放

resume 入口:run <wf> --resume <runId>   # 或 resume <runId>
重放模型 :脚本从头执行,每个 agent() 调用与上次 run 同位置记录比对
指纹组成 :id + prompt + schema + provider + model + 解析后 retry 策略
命中规则 :前缀全命中 → 逐个复用;首个分歧之后 → 全部实跑
loop     :前缀式缓存,在第一个分歧 loop marker 处停止
tool     :tool 调用结果同样缓存重放(自定义 tool 里的 Date.now() 也安全)
卫生要求 :循环内用稳定 id(round-N);Date.now/Math.random 触发非阻塞警告
落盘     :续跑写入全新目录,不污染旧 run;复用原 run 记录的精确 workflowFile(按名字解析可能已漂移)

Artifacts 目录布局

runs/<runId>/
  manifest.json  workflow.input.ts  config.resolved.json  run-input.json
  calls.jsonl    cache-index.json   events.jsonl          report.json
  agents/<agentId>/{prompt.txt, stdout.log, stderr.log,
                    raw-result.json, normalized-result.json,
                    schema.json, validation-error.json}
  pipelines/<id>/items/<i>/stages/<name>/stage-result.json
  workflows/<invocationId>/{input, result, error, summary}.json
  tools/<toolCallId>/{metadata, input, output, error}.json

默认值与优先级

concurrency 4 · timeoutMs 900_000 · maxLoopRounds 20 · maxDepth 8 · failFast false
retry 默认:maxAttempts 3 · delayMs 1000 · backoff exponential · maxDelayMs 30_000 · jitter true
          (省略 retry = 单次尝试;false = 显式禁用;超时/取消/安全违规不重试)
优先级    :agent DSL 参数 > CLI 覆盖 > profile/alias > YAML 配置 > 内置默认
outDir    :--out > profile.outDir > 顶层 outDir > 内置 runs/(独立解析)

安全模型

权限:默认 {mode:"default"} 不传写使能标志;dangerously-full-access 需注释理由
     映射:codex --dangerously-bypass-approvals-and-sandbox / gemini --approval-mode yolo
          / copilot --yolo / opencode·antigravity --dangerously-skip-permissions / cursor --force
env :redactEnv 默认脱敏 OPENAI_API_KEY、GEMINI_API_KEY、GOOGLE_API_KEY、*_KEY、*_TOKEN、*_SECRET、PASSWORD
     passEnv 默认 [](白名单外一律不传给 provider 子进程)
纪律:prompt/log 不得含密钥与完整私有源码;分享 runs 产物视为泄密面
