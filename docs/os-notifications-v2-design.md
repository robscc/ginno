# OS 通知 V2 —— 从「聊天回复完成」到「后台干活全景」（产品方案）

> 状态：**已拍板（2026-11-05），待实施**
> 决策记录：通知粒度=同会话 30s 合并；失败=差异化（⚠️+故障音）；正文=两档设置默认完整摘要；
> 开关=每类独立默认全开；点击路由=按类型直达；权限时机=维持现状；P1 增强包（workflow 聚合/
> 子代理回传/免打扰时段/隐私档）**全部排期**。
> 来源：特性雷达 2026-11-04 候选 #1。**注意：雷达的自查结论（「仓库无 OS 级系统通知」）有误**——
> Ginno 已有完整的原生通知机制，真实缺口是**触发面**，不是机制。本文按纠错后的现状设计。
> 工作量重估：MVP 约 1–1.5 天 + P1 半天（雷达原估 4–6h 是按「从零建」算的）。

| 「没在看才通知」判定 + 侧栏未读点 | ✅ 已有 | 同 handle.ts（`watching` 三条件：可见 ∧ 在 `/` 路由 ∧ 活跃会话） |

## 二、目标与非目标

**目标**：用户把活交给 Ginno 后台干（定时任务/workflow/子代理/审批等待），干完、失败、或需要人介入时，
**不在屏幕前也能知道**，且点击直达现场。这是本地优先应用「后台替你干活」承诺的最后一公里。

**非目标**：windows/linux 通知（现有机制即 macOS only，V2 不扩平台）；通知中心富交互（回复/按钮动作）；
渠道消息通知（用户就在钉钉/企微里聊，通知无意义）。

## 三、缺口：四类后台终态没有通知（按用户痛感排序）

| # | 场景 | 现状 | 事件链现状（接入成本） |
|---|------|------|----------------------|
| 1 | **ask_user 等人**：工作流/审批挂在 interrupt 等用户回答 | ❌ 无通知，不看就永远卡着 | `user.question` 帧已广播（engine.py:948），前端已处理渲染——只差挂通知 |
| 2 | **turn 失败**：后台任务报错（限流/网络/工具炸） | ❌ 失败与完成同路径，失败时可能无 `message.end`（走 error 收口），通知漏发或无差异 | `turn.error` 类帧已有，挂通知 + 标题前缀「⚠️」 |
| 3 | **workflow run 终态**：run 整体 done/failed | ⚠️ 各 step 的 turn 通知会响，但每步一条 = 刷屏；run 整体终态无通知、无聚合 | run 状态事件已有（workflow_run_status 的数据源），需广播 + 前端订阅 |
| 4 | **子代理结果回传**：spawn 的 subagent 完成注入主会话 | ⚠️ 注入产生新消息事件，但不走 `message.end` 路径 → 不通知 | subagent 结果注入有事件链（engine.py subagent_* 分支），补一档通知 |

**防噪反向缺口（同样重要）**：workflow 多步 run 每步 turn 都触发现有通知 → 一个 5 步 run 弹 5 条。
Claude Code 本周刚修「重复通知」的同类坑（雷达来源佐证）。V2 必须带**合并抑制**。

## 四、用户故事

1. 作为用户，我挂了个 09:00 的雷达定时任务去开会；10:02 它完成了，我看到一条系统通知
   「📋 特性雷达已生成（定时任务）」，点一下直接跳到那个会话看报告。
2. 作为用户，一个 workflow 跑到第 3 步 ask_user 需要我确认；我在写代码，弹出「⏸ 工作流等你回答」，
   点过去 30 秒解决，workflow 继续。
3. 作为用户，昨晚的长任务因限流失败了；通知是「⚠️ 任务失败：rate limited」而不是无声无息，
   我今早知道要重跑。
4. 作为用户，5 步 workflow 跑完只弹**一条**「✅ workflow 全部完成」，不是五条。
5. 作为用户，我在投屏演示，通知只显示「Ginno 有新结果」不显示正文（隐私档位）。
6. 作为用户，深夜跑完的任务不弹横幅不打扰家人（免打扰时段，仍进通知中心）。

## 五、产品决策点（含推荐）

| 决策点 | 选项 | 推荐 |
|--------|------|------|
| 通知粒度 | 每事件一条 / 同会话窗口合并 | **合并**：同会话 30s 内多条合一条（「3 个后台任务完成」）；workflow run 聚合为一条 |
| 失败 vs 完成 | 同款通知 / 差异化 | **差异化**：标题前缀 ⚠️ + 默认故障音（完成静音维持现状默认） |
| 正文隐私 | 完整摘要 / 仅标题 | **两档设置**，默认完整摘要（本地应用，正文进通知中心风险低；投屏场景用户自查隐私档） |
| 免打扰时段 | 无 / 可配时段 | **P1**：时段内不弹横幅不响（通知中心保留），默认关闭该功能 |
| 分事件开关 | 总开关一刀切 / 每类独立 | **每类独立**（定时任务/工作流/子代理/审批等待/失败），默认全开，设置页分组复用现有页 |
| 权限申请时机 | 启动即申请 / 首次事件时 | **维持现状**（test 按钮可申请）；V2 不改 |
| 点击路由 | 都去会话 / 按类型直达 | **按类型**：ask_user→会话+展开问题卡；workflow→run 详情页；复用 `kind` 字段（已有 `session`，新增枚举） |

## 六、分期

**P0（MVP，约 1–1.5 天）——「等人知道、失败知道、不刷屏」：**
1. ask_user 挂起通知（#1 缺口，`user.question` 已有事件，纯前端挂接）
2. turn 失败差异化通知（#2）
3. 同会话 30s 合并抑制（防噪）
4. 设置页按事件类型分组开关
5. 点击路由按 kind 扩展

**P1（约半天）——「锦上添花」：**
6. workflow run 整体终态通知（聚合，需 run 终态广播——runtime 侧小改）
7. 子代理结果回传通知（#4）
8. 免打扰时段 + 正文隐私两档

## 七、验收标准（P0）

- [ ] 后台会话 ask_user 挂起 → 3s 内收到系统通知，点击跳转并展开问题卡
- [ ] turn 失败 → ⚠️ 前缀 + 故障音；完成 → 与现状一致
- [ ] 同会话 30s 内 3 个 turn 完成 → 仅 1 条通知，正文「3 个后台任务完成」
- [ ] 设置页可独立关闭任一类通知；全关后行为与现状关闭一致
- [ ] 正在看该会话（watching 三条件）时：零通知（现有判定不动）
- [ ] vitest：合并抑制逻辑纯函数单测；e2e 沿用 fake-LLM 脚本路径
