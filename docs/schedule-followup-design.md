# 定时任务继续沟通（Schedule Follow-up）设计

> 2026-10-14 立项。现状：定时任务每次触发新建影子会话跑一轮 headless，
> 执行记录页只读回放（无 composer、无 WS）。用户看完结果经常想追问——
> 「这个报错怎么回事？」「按 xx 再调整一下」——目前只能另开新会话从头
> 交代背景，或等下一轮定时触发。本设计给影子会话接上沟通通道。

## 0. 核心洞察：影子会话是真实会话

`_run_prompt_target` 建的就是真实 session（checkpoint、graph、meta、
用量、`schedule_run_id` 关联一应俱全），「只读」纯粹是**产品姿态**不是
技术限制。继续沟通 = 把回放页从「只读 transcript」升级为「带 composer
的完整会话视图」——复用一切既有会话机制，几乎零新协议。

## 1. 产品方案

### 1.1 入口与形态（最小惊讶）

```
ScheduleRunView（现在的只读回放页）
┌──────────────────────────────────────────────────────┐
│ ⏰ PR 状态巡检  ✓成功 · 14:02 · 1m12s · ↑12.3k ↓890   │
│──────────────────────────────────────────────────────│
│  …transcript（现有只读渲染，原样保留）…                │
│  [user] 巡检三个仓库的 PR                             │
│  [assistant] 3 个 PR 待审，其中 #42 冲突…             │
│──────────────────────────────────────────────────────│
│ ┌────────────────────────────────────────────────┐   │
│ │ 继续沟通：输入框 + 发送                          │   │   ← 新增
│ └────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────┘
```

- **执行终态（ok/error）后**：transcript 底部出现 composer（placeholder
  「就此结果继续沟通…」）。运行中不出现（turn 正在跑）。
- 首条追问**原位追加**到 transcript——影子会话从此就是一个可继续的会话。
- **不改变隐藏语义**：影子会话仍不进会话列表/搜索（现有过滤原样）；
  想把它「转正」见 §1.4。

### 1.2 通信机制（复用会话通道）

- 回放页挂载时建**该会话的普通 session WS**（`/api/ws/sessions/{id}`），
  复用 engine 的连接管理（ping/重连/turn_state 探针/孤儿认领——全部白拿）。
- 发送 = 标准 `invoke`。运行中再输入走 `steer`（多轮沟通天然支持）。
- **权限交互**：headless 跑时 `_set_interactive_turn(False)` 让 ask_user
  静默降级；**用户在场沟通时应是交互态**——composer 路径以「用户 turn」
  身份发起（与手输 invoke 同语义），ask_user/permission 卡照常可答。
  简化实现：runtime 侧不区分来源，invoke 由 WS 进来天然是用户通道；
  只有 scheduler 自己的 headless 轮保持 non-interactive。
- 事件回填：现有 WS 事件流（token.delta / tool.* / subagent.* …）驱动
  transcript——回放页从「5s 轮询 history」升级为「初始 history + WS 增量」。

### 1.3 与定时任务生命周期的关系

| 场景 | 行为 |
|---|---|
| 下一次定时触发到点 | **新建影子会话**（现状不变）——定时轮次隔离、可并行回看；**不**在旧影子会话里续 |
| 用户沟通期间又到点 | 互不影响（两个真实会话）；执行记录各自一行 |
| 手动「立即执行」 | 新影子会话（现状） |
| 回放页运行中用户关页 | turn 不中断（服务端执行）；重进继续看 |
| 影子会话删除 | 执行记录保留；行点击 → 「会话已删除」空态 |

> 设计取舍：**不在旧影子会话里续定时轮**——定时任务的价值在「每轮独立、
> 可对比、无状态漂移」；一旦续聊，上下文越滚越偏，巡检类任务的基线就毁
> 了。继续沟通是**用户对某一轮结果的深入**，自然归属那一轮的会话。

### 1.4 转正（fork to regular session）

P1（本期）：回放页顶栏加「转为普通会话」按钮：
- patch meta：`type` 去掉 `scheduled` + 清 `schedule_run_id` → 立即出现在
  会话列表（标题保留 ⏰ 前缀供追溯，用户可改名）
- 原任务不受影响（下一轮照常新建影子会话）
- 深链清理：执行记录行点击该 run 时仍能进回放（按 schedule_run_id 查），
  会话已是普通会话则进普通会话视图

P0 不做转正，只做 composer——先验证沟通频次。

### 1.5 运行中观察（P1 增强）

回放页运行中（轮询刷新的 5s 窗口内）也允许输入：文本进入 steer 队列，
turn 结束前被吸收。P0 先只做终态后沟通（运行中 composer 隐藏，避免与
「轮询刷新」的渲染竞态——P1 接 WS 后自然解锁）。

## 2. 实现拆解

### 2.1 前端（主体工作）

1. `ScheduleRunView` 升级：
   - 挂 `useChatStreamEngine`（或其子集：socket + 事件处理 + send）——
     设计文档 §3.6 曾倾向「抽出纯渲染 transcript 子组件」避免背 engine
     复杂度；**继续沟通后这个理由反转**：既然要完整交互，直接复用 engine
     比再造一份发送管线便宜。落法：把 transcript 渲染部分对齐 ChatStream
     的消息 store 消费形态，engine 以「非主导」模式挂载（无 active session
     争夺、不参与 codeWatch 等副作用）。
   - composer：复用 ChatStream 的输入组件（去掉 @/斜杠菜单也可，最小化
     surface——首版纯文本 + 发送）。
   - 运行中：保留 5s 轮询渲染（P0），终态即挂 composer。
2. 侧栏上下文：从 `/scheduled` 进入回放时，右侧工作区保持 hidden（现状），
   无需改动。
3. 转正按钮（P1）：`PATCH /api/sessions/{id}` 已支持改 title 等——需确认
   可改 `type`（不可改则加一个 `unschedule` 端点，2 行）。

### 2.2 runtime（几乎零改动）

- WS/invoke/steer 路径零改动（影子会话就是普通会话）。
- 可选：`CreateSessionRequest` 或 meta patch 允许 `type: scheduled → user`；
  执行记录查询按 `schedule_run_id` 兜底（已存）。
- 边界：影子会话沟通的 turn 走 `usage_source="chat"`（用户在场，记账如实）。

## 3. 边界与安全

- **隐藏语义不变**：不转正的影子会话永远不进列表/搜索（现有过滤不动）。
- **权限**：用户沟通触发的 turn 与手输无异——权限卡、ask_user 照常交互；
  不因「定时任务出身」放宽任何门禁。
- **并发**：同一影子会话同时只有一个 turn（既有 busy 门天然管住）；跨
  会话（新旧轮次）互不干扰。
- **数据**：沟通内容写进同一 checkpoint——回放/审计/用量天然完整。
- **过期清理**：影子会话保留策略不变（现状：永久保留，删除任务不删会话）。

## 4. 分期

| 期 | 内容 | 判据 |
|---|---|---|

| P1 | 转正按钮 + 运行中 steer + composer 富功能（@/斜杠） | 一键转正后出现在侧栏 |
