Ginno Runtime · 机制速览

一个会话怎么诞生，
一条消息怎么流回屏幕

前端是 Next.js，运行时是 Python sidecar（FastAPI，127.0.0.1:8787）。 会话不是一条数据库记录，而是「磁盘 meta + 内存 graph + 文件 checkpoint」三样东西的组合； 消息回传不靠轮询，靠一条 WebSocket 上的广播事件帧。

01会话的诞生

入口只有一个：POST /api/sessions → create_session()（api/sessions.py:550）。 五步之内，一个 id 贯穿所有产物：

谁还会走这个入口：定时任务的影子会话（type="scheduled"）、subagent 派生、团队成员（team-member）、workflow 的 fork agent—— 全部经由同一个 create_session()，只是 type 与载荷不同。
  • 重启后_ensure_session(id)（api/sessions.py:1238）从磁盘 meta 懒重建 graph 并塞回 _SESSIONS——会话因此活得比进程久。
  • 热切graph 持有 model_getter 而非裸模型引用，运行中 PATCH 换模型对在途 turn 也生效。

02一条消息的往返

前端对每个会话开一条 WS（ws://…/api/ws/sessions/{id}）， 服务端把 socket 挂进 _SESSIONS_WS[id] 广播注册表，然后进入接收循环。 你按下发送，走的是这样一条链：

  • steerturn 进行中再发的消息走 {type:"steer"}：不入队新 turn，而是暂存进 steer 队列，由运行中 turn 的下一个 agent 超步「吸收」进上下文，前端只收一条 steer.accepted / steer.absorbed 标记。
  • 停车工具要权限 / ask_user 提问时，graph 在 interrupt 处停车：帧变成 permission.request / user.question，等前端回 permission_response / user_answer 再 Command(resume) 续跑。

03事件帧：消息的运输形态

每一帧都是一行 JSON（_ev() 拼装，server_shared.py:428），两个记号负责「不串台」和「归组」：

{ "event": "token.delta", "frame_session": "a1b2c3…", ← 帧归属：不属于本会话的帧直接丢弃（结构上杜绝跨会话渲染泄漏） "turn_id": "9f0e…", ← 帧归组：前端按 turn_id 把 delta 归进对应气泡 "content": "好的，我先看一下文件" }

广播语义是刻意设计：服务端遍历 _SESSION_WS[id] 里所有活 socket 逐个发送 （_push_session_event），发挂的顺手从注册表剔除。于是多开 tab 同见一条流， headless turn（定时任务、goal 续跑）没有「发起 socket」也照样能被任何连着的 tab 看到。

04断线、重启与恢复

事件是火过就没的，真相在盘上。三样持久化兜住了所有「回来再看」的场景：

CHECKPOINT

FileCheckpointer

LangGraph 每个超步追加写。/history 从它回放消息；retry_from_checkpoint、定时任务续跑从它断点继续。

META

会话索引 JSON

标题、agent、provider/model、挂载文件夹。重启后重建 graph 的唯一依据。

SOCKET

重连三件事

① 发 turn_state 探针：还跑着就继续听流；② checkpointer 里有挂起 interrupt → 重发权限/提问卡；③ 不在跑 → 对账 /history。

所以「页面显示运行中」从来不是前端自己猜的——它要么正在收这个会话的帧，要么收到了 turn.state.running: true。 一旦 turn 结束，message.end 触发一次 /history 对账，气泡与磁盘状态严格一致。

05并发模型：协程，还是子进程？

全部控制流都是同一个 Python 进程里的 asyncio 协程——没有「每会话一个进程」。 真子进程只出现在工具执行层：shell 命令、外部代理 CLI、Node 的 mod-runner。

「不连 WS，会话协程就不启动？」——不会。会话不是协程，是内存条目 + 磁盘状态；create_session 走 HTTP， turn 也不需要任何 socket：定时任务影子会话、goal 续跑、subagent 全是 headless 跑的。 真正「连了才存在」的协程只有两个：WS 接收循环（invoke / stop / steer 的唯一入口）和文件 watcher （在 session_ws 里 spawn，断开即停）。

06多会话会打架吗：竞争与闸门

会。但不是锁打架——单线程协作式调度下，两次 await 之间的同步代码是原子的， 危险的「读-改-写跨 await」都有显式闸门。真正的瓶颈在进程外面：共享的 provider 配额。

  • 数据侧按会话分桶的 dict（key = session_id）结构上不共享字段；跨 await 的复合操作全部有闸：busy check、check-and-discard（两 tab 抢答只一个赢）、identity-checked pop（不误删后继任务）。
  • 卡死侧每 turn 180s chunk 看门狗（CHUNK_TIMEOUT_S）：停流的 turn 快速报错让位，不无限占坑。
  • 何时警惕若未来有会话内联做 CPU 重活（同步解析大文件再进上下文），它会让所有会话的流一起卡——照 checkpointer 的样子 to_thread 下去。

07线程池是共享的，隔壁为什么零感知

因为共享的是「工人总数」，不是「单个工人」。A 的 glob 领走 1 号工， B 的工具直接领 2 号工——而两个协程在 submit 之后立即挂起， 事件循环连一纳秒都没有替它们等待。

唯一会漏到隔壁的路径：纯 CPU 的 Python 代码在线程里长跑，会和主线程抢 GIL（毫秒级顿挫，不是卡死）。 glob 的答案是把 CPU 重的匹配交给 rg 子进程（另一个进程，GIL 都不共享），自己线程里只做 readdir 这类释放 GIL 的 IO。 32 个工人全忙时新工具会排队——但等的是「轮到自己」，循环照常推流。
